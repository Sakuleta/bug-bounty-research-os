# HTTP / Edge / Cache

> SCOPE: Load when the target sits behind a CDN, reverse proxy, WAF, or cache, or when HTTP parsing behavior itself is the research surface.

## Research families

Request-boundary families — a front-end and a back-end disagree about where a request ends:

- HTTP/1.1 request smuggling and desync (CL.TE, TE.CL, TE.TE, H2.CL, H2.TE)
- Dangling-byte and zero-length prefix attacks (0.CL, CL.0)
- Client-side and browser-powered desync
- Response queue poisoning (no cache required)
- CRLF-powered / header-injection desync — an injection primitive (canonically an Nginx `proxy_pass http://backend$uri` or `return 302 $uri` directive, where `$uri` is URL-decoded so `%0d%0a` re-becomes a real CRLF) that turns one request into a smuggled prefix, a request split, or an injected `Content-Length`/`Transfer-Encoding`. Header injections are not low-impact bugs; a single injectable header is enough for a CL.TE desync.
- Request tunnelling — the front-end and back-end sockets are not shared, so the primitive is blind; distinct from smuggling because cross-user exploitation is blocked (non-blind HEAD and `Expect: 100-continue` variants recover the response)
- Reverse desync — response header injection / response splitting against a keep-alive origin (Amit Klein's 2004 lineage), now mostly blocked by browser/edge over-read
- Hop-by-hop framing abuse — an intermediary removes a header named in `Connection` at one hop but not the next, so the two hops frame the same message differently (RFC 9110 §7.6.1 mandates the removal; RFC 9113 §8.2.2 says H2 must treat such fields as malformed)
- Shared-parser confusion (one parser instance reused across logically separate components) and response forking — both surfaced as *classes* by the 2026 HTTP Terminator work; response forking was seen but never proven in the wild

Cache families — the cache and the origin disagree about what identifies an object or what is private:

- Web cache poisoning via unkeyed inputs
- Web cache deception (path / static-extension / delimiter confusion)
- Cache-key normalization differentials (query ordering, delimiter and encoding handling, cookie allowlists)
- Cache parameter cloaking, unkeyed query strings, and fat GET (origin reads the body or a cloaked parameter the cache did not key)
- Cache-key delimiter collisions (key built by concatenating components without escaping, so two different requests produce one key)
- Application-layer / fragment caches with no real cache key (WordPress plugins and similar), which can be poisoned through internal-only pages

Header / routing / version families:

- Host and forwarded-header routing differentials
- HTTP/2 frame and pseudo-header differentials (CONTINUATION, CONNECT, SETTINGS)
- HTTP/3 / QUIC intermediary mismatches (0-RTT replay, migration, downgrade, connection coalescing)
- Gateway and backend path/method normalization gaps
- Duplicate header and parameter precedence at the edge
- WAF vs origin normalization mismatch (the WAF inspects a decoded/normalized view; the origin receives the raw or differently-decoded value)

Trigger/gadget framing ties the families together: every desync finding is a **trigger** (a parsing ambiguity the pair resolves differently) plus a **gadget** that converts the smuggled prefix into impact (a queue, a cache, a redirect target, a stored-prefix reflection, a HEAD/over-read, a `Range` window).

### Where the families cluster (edge fingerprints)

- A CDN edge terminating H2/H3 in front of a Node/Rails/Python origin is the classic H2.CL/H2.TE surface (the edge speaks frames, the origin speaks `CL`/`TE`).
- Envoy or an AWS ALB in a service mesh in front of an H1 upstream is where generated-request smuggling lives (header escaping, upgrade handling, unresolved body debt, path-normalization options).
- Nginx/OpenResty/Tengine with `$uri` inside `proxy_pass`/`return` is where CRLF header injection lives — any reflected injection point (path, custom upstream header, cookie) can become a desync.
- Varnish/Fastly in front of a framework that disagrees on path delimiters is where cache deception lives.
- A shared upstream pool plus any desync trigger is where response queue poisoning lives; without pool sharing the same trigger degrades to tunnelling.
- CloudFront always speaks HTTP/1.1 to custom origins (viewer side may be H2/H3), so a CloudFront-to-origin hop is itself an H2→H1 translation surface — but the documented header table removes `Expect` and `TE` before the origin, so Expect/TE-header triggers must be assessed on a different hop.
- Akamai Ghost ran an in-path desync (Expect-based, obsolete line folding) inside its own infrastructure — patch boundary 2025-03-26.
- Apache Traffic Server carried a desync trigger found by the HTTP Terminator (CVE-2026-63078); the `Server: ATS` banner plus a `TRACE`/`DELETE` pair in one response is the fingerprint.

## Preconditions

- At least two HTTP-speaking components in series (front-end plus origin), or a cache layer whose key is observable.
- A request ambiguity the two components resolve differently (Content-Length vs Transfer-Encoding, H2 pseudo-headers vs H1 translation, trailing bytes after a zero Content-Length, connection-specific headers that one hop strips and the next does not).
- For cache poisoning: a cacheable response (static extension, 200 with cache headers, or CDN default caching) plus at least one unkeyed input reflected into the response.
- For response queue poisoning: a shared upstream connection (keep-alive reuse) so a desynced prefix corrupts the next queued response. The shared socket may be per-client (connection-locked), per-public-IP (IP-locked), or truly pooled; only the pooled/coalesced case yields ordinary cross-user impact, the others need browser-powered delivery.
- For browser-powered desync: attacker-influenced cross-origin request the browser will emit (form, fetch with no-cors, navigation) that reaches the vulnerable connection path.
- Dangling-byte variants need a backend that tolerates a request ending mid-byte or with Content-Length: 0 while the front-end forwards trailing bytes.
- QUIC/H3 variants need an H3-capable edge with H1/H2-only origin behavior behind it, or an H3 client completing a request at the transport layer while it still carries a nonzero `Content-Length`.
- For trigger/gadget chaining: a parsing ambiguity (trigger) plus a downstream primitive that converts a smuggled prefix into impact (gadget: cache write, redirect target, stored prefix reflection).
- For CRLF/header-injection desync: a front-end (very often Nginx, OpenResty, or Tengine) that reflects or forwards an attacker-controlled string into the upstream request — path, a custom upstream header, or even a request cookie — without stripping CRLF; injection points outside the path are the least-exhausted surface.
- For a hop-by-hop differential: a proxy that honours `Connection: X` (removing field `X` before forwarding) behind a hop that does not, or the reverse; RFC 9110 §7.6.1 says intermediaries MUST do the removal, so the gap is the non-compliant side.
- For WAF-normalization abuse: a WAF that decodes/transforms only for inspection (AWS WAF transformations) or an edge that normalizes before rule evaluation (Cloudflare normalization) while the origin still sees the original bytes.
- For cache deception, both sides must be cacheable *and* origin must treat the decorated path as the dynamic route: Cloudflare caches only `GET`, skips responses with `Set-Cookie`, and applies per-status default TTLs (200/206/301 120m, 302/303 20m, 404/410 3m); CloudFront always caches `GET`/`HEAD` (and `OPTIONS` only when configured), never other methods.

### Choosing the oracle: queue poisoning vs cache poisoning

Fingerprint the connection-reuse model *before* picking an oracle; the wrong choice wastes the window and can expose data you never intended to touch.

- Coalesced/shared upstream pool (HTTP/1.1 keep-alive reused across clients, or HTTP/2 connection coalescing under a wildcard cert): **response queue poisoning** is available and catastrophic — one desynced prefix makes the front-end mis-map *all* later responses on that socket. No cache required.
- Per-client keep-alive / connection-locked: the corruption is confined to your own socket; use **cache poisoning** (a gadget writes to the shared cache) or move the trigger into the victim's browser (browser-powered desync) to reach cross-user impact.
- Per-public-IP (IP-locked): impact is limited to users on the attacker's egress; again move the attack into the victim's browser.
- No shared socket and no cache gadget: only **request tunnelling** remains (self-impact; useful for access-control bypass, not for "users get wrong responses").
- Cache poisoning additionally needs a *cacheable* response and an unkeyed input; if the response is uncacheable, prefer queue poisoning or tunnelling over forcing a cache oracle.
- Attack-shape cheat sheet: connection-locked → keep sending on your own keep-alive connection and use a HEAD/`Range` gadget to leak into your own response; IP-locked → inject a header (e.g. `Expect`) and use the shared egress; pooled → full RQP; cache available → queue a cache write and stop.

## Oracles

Desync oracles (timing/queue):

- Timing differential: a smuggled prefix that triggers a backend delay (sleep, slow collaborator fetch) shifts response time on the *following* normal request, not the probe itself.
- Response cross-contamination: normal request returns another request's status line, headers, or body fragment (queue poisoning confirmed without cache).
- Dangling-byte probe: request with `Content-Length: 0` plus trailing bytes returns a normal response now, but the *next* request on the connection 400s or reflects the trailing bytes (prefix captured).
- Dangling-byte (HTTP Terminator): send the smuggled request missing exactly **one byte** — the second response is not generated until the victim's request supplies that byte, which removes the RQP race window entirely; extremely effective against method-agnostic backends.
- Early-response gadget probe for 0.CL: prove the back-end answers without waiting for the body (`/nul`, `/con` on IIS, `/con`-style reserved names, nginx static-file early response, server-level redirects). No gadget, no exploitable 0.CL — the two components deadlock instead.
- `Expect`-driven 0.CL/CL.0: a valid or lightly obfuscated `Expect: 100-continue` (`Expect: y 100-continue`, `Expect:` + folded value) makes some front-ends forget they still owe the back-end a body — the cheapest 0.CL/CL.0 trigger found at scale (Akamai CVE-2025-32094 is one).
- H2 downgrade signal: pseudo-header case variation (`:path` vs `:Path`), duplicate `:authority`, or smuggled `Content-Length` inside DATA frames produces different backend routing than the direct H1 equivalent.
- Header-injection status oracle: injecting a syntactically invalid line produces the *front-end's* neutral code, but an ambiguity the origin parses produces the origin's code — e.g. `HTTP/13.37` → `505 Version Not Supported`, `Transfer-Encoding: x` → `501 Not Implemented` (RFC 9112 §6.1 says a server SHOULD return 501 for a transfer coding it does not understand), `Expect: asdf` → `417 Expectation Failed`. A status the edge would never emit proves the injected line reached the origin.
- Masked `Content-Length` probe (0.CL shape): `Content-Length:` followed by a newline and a space-indented value hides the header from a front-end while the back-end parses it — the classic H-V basis for a 0.CL desync once an early-response gadget is available.
- Discrepancy class picking: after a masked-header probe finds a **V-H** discrepancy (front-end sees, back-end hides), prefer a **CL.0** exploit over TE.CL — hiding `Content-Length` is far less likely to trip a WAF than a `Transfer-Encoding` probe.
- `Expect: 100-continue` over-read: when the front-end receives an unexpected `100 Continue` from the origin it may read until the connection closes, dumping the smuggled response back to you (turns a blind tunnelling primitive into a visible one). The same `Expect` trick can make the edge *skip* stripping sensitive response headers — and an *injected* `Expect` header exposes the edge's internal headers (`x-fd-int-roxy-*`, origin-IP/upstream-error fields) as well.
- Nested / stacked response: two responses concatenated for one request (a small over-read where the edge forwards the extra bytes instead of discarding them) — a narrow race window, but enough to append a whole extra response to live users.
- Masked-header discrepancy (Request Smuggler 3.0 style): a partly hidden header (`Content-Length`, `Host`, `Transfer-Encoding` with a leading space) that yields a unique response proves a parser discrepancy, and the direction (V-H: front-end sees it, back-end hides it; H-V: the reverse) tells you whether to try CL.0/TE.CL or CL.TE/H2.TE. Status codes do not matter, only that they differ.
- Blind (tunnelling) vs cross-user (smuggling): if the prefix only ever affects *your own* next response, the socket is not shared — this is tunnelling; escalate by moving the trigger into the victim's browser (fetch / navigation) so *their* connection carries it.

Cache oracles:

- Cache-hit header flip: second identical request returns `HIT` where the first returned `MISS`, with attacker-controlled content stored (poisoning confirmed).
- Unkeyed-input reflection: change `X-Forwarded-Host`, `X-Original-URL`, `Accept`, or an unkeyed cookie and observe the change persist for a clean-cache-busting request from a second session.
- Cache deception: `/account/profile.css` or `/account;.css` returns the authenticated account body with a cacheable content-type and is retrievable anonymously.
- Response header manipulation via the cache: `CDN-Cache-Control: private="Location"` (Cloudflare) tells the cache to strip a named response header (e.g. `Location`), which can turn a response-header injection into an XSS on a redirect.
- 0-RTT replay: replayed early-data request executes a state change twice (only test on explicitly idempotent-safe endpoints; otherwise infer from response equality, never double-spend).
- Trigger/gadget separation: the same smuggled prefix produces no impact alone but poisons or redirects when paired with a gadget endpoint — confirms exploitability class without demonstrating victim impact.
- Key-disclosure oracle: on Akamai, `Pragma: akamai-x-get-cache-key, akamai-x-get-true-cache-key` returns `X-Cache-Key` / `X-True-Cache-Key` (plus `X-Cache-Key-Extended-Internal-Use-Only`); the three keys disagreeing exposes exactly which components (port, query, cookies, `Origin`) are keyed. Treat as historical — vendors have since suppressed such disclosure.
- Unkeyed-query-string oracle: change a query value and look for any response change; if the response is identical *and* a cache-buster in a normally keyed header (`Origin` on Cloudflare) still returns `HIT`, the whole query string is out of the key and the page looks static.
- Parameter-cloaking oracle: a target that removes only one parameter from the key can be tricked into dropping arbitrary parameters — e.g. a Varnish regex `\?_=[^&]+&` lets `?q=help?_=payload&!&search=1` poison `q`; Rails treats `;` as a parameter separator, so `?callback=legit&utm_content=x;callback=alert(1)//` keys on `callback=legit` while Rails reads the second `callback`.
- Fat-GET oracle: `GET` with a body (form-encoded) whose parameters the origin reads but the cache does not key; Varnish `builtin.vcl` strips the body, Rack::Cache and Cloudflare historically forwarded it unkeyed.
- Method-out-of-key oracle: replay a `POST` body as a `GET` (or vice versa) and see whether the cached response follows — many caches key only the URL.
- Path-variant cache busting (same endpoint, different key): Apache `//`, Nginx `/%2F`, PHP `/index.php/xyz`, .NET `/(A(xyz))/`.
- Cache-key normalization oracle: send an encoded delimiter (`%3f`, `%6c`) and compare the cache status with the decoded request; if both `HIT` the same object, the key is decoded/normalized and the raw request reached a different origin path.
- Key introspection on Cloudflare: send the request through Cloudflare Trace; a cache hit shows a `Cache Parameters` section with a `View parameter detail` view listing exactly which Cache Key properties were used — read the key instead of guessing it.
- Deterministic single-node testing on Fastly: `Fastly-No-Shield: 1` in `vcl_recv` disables clustering/shielding for the request, so you observe one node's behaviour instead of a delivery/fetch-node pair; clustering is also skipped after a `restart` or a `return(pass)`/`error` from `vcl_recv`.

### Connection-reuse fingerprinting (run before any queue oracle)

- Send two back-to-back requests on one keep-alive connection; if a desync prefix from request 1 alters the response to request 2, the socket is at least connection-locked.
- Repeat from a second network egress (mobile hotspot / VPN); if the prefix also affects the second egress, the upstream socket is shared and queue poisoning (cross-user) is viable.
- On HTTP/2, test connection coalescing by reusing one connection for a second hostname covered by the same certificate; a desync that surfaces the *other* host's responses confirms a coalesced origin path.
- Compare the edge's `Connection`, `Keep-Alive`, `Via`, and `X-Cache`/`CF-Cache-Status`/`X-Served-By` headers to identify which hop is pooling (CloudFront sets `Via: <ver> <id>.cloudfront.net (CloudFront)` on the response).
- Queue oracle read-out: a second canary session whose request carries no payload of its own returns *your* prefix or another request's bytes.
- Coalescing hygiene check: request a second host on the shared connection and look for `421 Misdirected Request`; a server that never emits it while serving the other host is a connection-contamination candidate.

### Trigger/gadget chaining (how a prefix becomes impact)

1. Trigger — a parsing ambiguity the pair disagrees on (dual-matching `Content-Length`, injected `Transfer-Encoding`, H2.CL, dangling byte, masked header line, `Expect`-driven body debt, `multipart/byteranges` on a `POST`, HTTP/1.0 + `Transfer-Encoding: gzip`).
2. Early-response gadget — makes the back-end reply before the body arrives, escaping the 0.CL deadlock (`/nul`, `/con`, static file, server redirect, `OPTIONS *?xyz` on Apache, `Expect` on many stacks).
3. Queue gadget — the smuggled complete request desynchronizes response mapping (queue poisoning) or request mapping (prefix attack).
4. Cache gadget — the smuggled request writes attacker content into a cacheable response (HEAD technique, `Range` window, a stored-prefix reflection, a redirect whose `Location` the cache stores).
5. Redirect/response gadget — injected `Location`/`Set-Cookie`, or response-header manipulation such as `CDN-Cache-Control: private="Location"`.
6. Exfiltration gadgets — stored-prefix capture (write captured requests into a field you can read, e.g. a nickname), `Range` slicing a stacked response to extract a closing tag or a `Set-Cookie` value, blind XSS with a Collaborator callback, QR-code delivery to mobile clients.
7. Subresource gadgets — poisoning a cacheable JS/CSS resource (or abusing relative-path overwrite) so every page that imports it executes attacker CSS/JS, even cross-domain; the classic "unexploitable" reflection that becomes critical once it is stored.
8. Impact gadget — a sink that turns the cached/mis-mapped content into XSS, open redirect, or credential capture; needed to prove impact, not to prove the desync.

## Minimal safe proof

1. Baseline: send the target request twice from two clean sessions; record status, cache headers (`Age`, `X-Cache`, `CF-Cache-Status`), body hash, and timing median over 5 samples.
2. Non-destructive ambiguity probe: send a single request with a harmless differential (e.g. duplicate `Content-Length: 4` / `Content-Length: 4`, or `Transfer-Encoding: xchunked`, which a conforming recipient should reject with 501 / 400 but lenient backends may ignore) and confirm identical handling; stop if the server 400s or closes — record as negative, do not escalate.
3. Timing oracle only: if step 2 shows tolerance, send one CL.TE-style probe whose smuggled prefix points at a delay endpoint you control (collaborator sleep, never a destructive action); measure the *next* request's latency, never the probe's.
4. Cache oracle only: reflect a canary string (unique token, no script) through one suspected unkeyed input; fetch the same URL with a cache-buster from a second session and check for the canary.
5. Deception check only: request the `.css`-suffixed authenticated URL anonymously in a fresh profile; compare body hash against the authenticated baseline.
6. Header-injection check only: append a `%0d%0a`-delimited invalid line to each candidate insertion point (path, custom upstream header, cookie) and read the status code; a response the edge cannot generate proves the line reached the origin. Never forward a payload that would be reflected to a third party.
7. Hop-by-hop check only: add `Connection: <framing-field>` (e.g. `Transfer-Encoding`) and compare framing behaviour with the same request without the option; a hop that strips on your instruction but a hop that does not is the differential to chase.
8. Vendor-aware stops before escalating: CloudFront returns `403` for a `GET` with a body and removes `Expect`/`TE`/`Upgrade` before the origin; a CloudFront-fronted target therefore cannot run Expect-based triggers at the origin hop. ALB `Strictest` rejects non-RFC-7230 requests before the origin sees them.
9. Stop conditions: any 5xx spike, session invalidation of another user, cached poison visible to a third party, or WAF block — halt, record, and report the oracle; never weaponize a poisoned cache entry or chain a desync into another user's session.
10. Fingerprint before choosing the oracle: name the hop path (client → edge → origin) and the connection-reuse model (coalesced pool, per-client keep-alive, per-IP) before claiming cross-user impact.

### Representative trigger shapes (from published research)

- Header-injection status oracle (Nginx `$uri` decode): `GET /%20HTTP/1.1%0d%0aContent-Length:%20X%0d%0aX:%20x` → the origin answers `400 Bad Request`, proving the injected line reached it.
- Version/verb oracles: injected `HTTP/13.37` → `505 Version Not Supported`; injected `Transfer-Encoding: x` → `501 Not Implemented`; injected `Expect: asdf` → `417 Expectation Failed`. Any of these that the edge itself would never emit proves upstream injection.
- Request split (double CRLF): smuggle a complete second request (`Connection: keep-alive%0d%0a%0d%0aGET / HTTP/1.1…`) → stacked responses / response queue poisoning. Response header injection variant: `GET /%0d%0aSet-Cookie:%20Sess=abc%0d%0a%0d%0a`.
- CRLF-powered CL.TE: inject `Transfer-Encoding: chunked` as a header on an otherwise normal `POST`, then use the timeout technique to confirm the origin consumes the chunked body while the front-end uses `Content-Length`.
- Dangling byte / partial byte: send a request whose framing leaves/consumes exactly one byte at the boundary (missing-byte variant or `Content-Length: 0` + body), then check whether the *next* request on the connection is prefixed (0.CL) or repurposed (CL.0); convert 0.CL→CL.0 with a double-desync when needed.
- Dual-matching `Content-Length`: two `Content-Length` headers with the same value (`Content-Length: 1` twice) — the HTTP Terminator found many stacks accept this and still desync; the harness bug that broke dual-CL requests had been masking vectors for months.
- `Expect: 100-continue` recovery: prepend `Expect: 100-continue` to force the front-end into an over-read that returns the tunnelled/smuggled response (`100 Continue` followed by the second response).
- `multipart/byteranges` CL.0: `POST` with `Content-Type: multipart/byteranges; boundary=BOUND` and `Content-Length: N`, payload directly in the body (the "payload after the terminator" variant did not work on any target) — exposed 200+ sites including a bank.
- HTTP/1.0 + TE: `GET / HTTP/1.0` with `Transfer-Encoding: gzip` and `Content-Length: N`; RFC 9112 §6.1 (quoted in the HTTP Terminator paper) says a recipient that receives an HTTP/1.0 message containing `Transfer-Encoding` MUST treat the framing as faulty, even with `Content-Length` present — the disagreement is the trigger.
- HEAD + `Range` sizing: use a `HEAD` request (no body expected) plus `Range: bytes=a-b` to control the over-read window length; stack a second request to fetch the missing tail (`</script>`) or to push a `Set-Cookie` line into the body.
- Hidden-vs-visible `Content-Length` (0.CL): `Content-Length:` + newline + leading-space value (`Content-Length:\n 7`) is invisible to the front-end, which then treats the following bytes as a second request while the back-end waits for a body. Pair with an early-response gadget (`/con` on IIS, `/nul`, static file on nginx) or the connection deadlocks at `504`.
- Browser-powered delivery of the same trigger: most CRLF-powered desyncs are fetch-spec compatible, so `fetch("https://target/%20HTTP/1.1%0d%0aHost:%20target%0d%0aConnection:%20keep-alive%0d%0a%0d%0aGET%20/%20HTTP/1.1%0d%0aFoo:%20bar")` reproduces the split without raw TCP; for connection-locked desync, get two requests onto one browser connection (`window.open()` + `location` reassignment, or rapid hidden-iframes) — Chrome allows one `window.open` per user gesture, so a click buys another pair of requests.
- Double-desync offset rule: front-ends usually append their own headers at the *end* of the header block, so a smuggled request that starts before those insertions survives unchanged; discovering the injected-header size (the `0cl-find-offset` Turbo Intruder script) is only needed when the attack depends on slicing into the appended block.

## False positives

- CDN `HIT` on public static assets with no attacker influence — rule out by confirming the canary is absent from the cached body.
- Timing jitter from edge PoP routing or TLS resumption — rule out with 5-sample medians plus a known-benign control request interleaved.
- Backend 400 on duplicate Content-Length that *both* layers reject identically — that is consistent rejection, not desync; a desync needs divergent handling.
- HTTP/1.1 pipelining mistaken for smuggling — pipelining is standards-compliant request concatenation the origin handles correctly in order; a true smuggle desynchronizes the queue. Distinguish with a pipelined pair whose second response is computed from the first request's effect.
- `X-Cache: HIT` reflecting only `Age: 0` or per-PoP headers — cosmetic headers, not poisoning; require stored attacker content.
- Reflected `X-Forwarded-Host` that is never cached and never used in links or resets — unexploited reflection, not poisoning; require persistence plus a security-relevant sink (reset link, canonical URL, script src).
- Deception-suffixed URL returning a login page or error with matching cache headers — the cache stored the *error*, not private data; require authenticated body bytes. Cloudflare's per-status default TTLs (404/410 for 3m) make cached errors look like hits.
- QUIC 0-RTT duplicate that the server deduplicates via replay cache — rule out by checking for a single server-side effect in logs/state, not client-visible duplication.
- Smuggled prefix echoed in an error page served only to the sender — self-reflection without queue or cache effect; require the follow-up request or second session to show contamination.
- Deception-suffixed URL caching only the `Vary`-differentiated anonymous variant (login page cached, account body never cached) — the cache keys the auth state correctly; require the authenticated body stored.
- Stacked-response blocked: a reverse desync that produces two responses locally but is dropped because the browser/edge over-reads and closes the connection on excess bytes — over-read tolerance is the difference between a working reverse desync and a dead one. RQP inherits the same race; if the front-end resets on extra bytes, the corruption is intermittent, not absent.
- Header injection accepted but not exploitable: the injected line lands in the *response* header block but after the redirect's `Location`, so the browser still follows the redirect — not a clean response-splitting win. (`CDN-Cache-Control: private="Location"` is the documented bypass for that blocker.)
- Malformed-response 400 rendered by the edge mistaken for a smuggled second request — require the second response to carry a *different* request's data (another user's body/session), not just an error page.
- Cache-key injection (`Vary` / a keyed header) mistaken for poisoning — if the payload returns only to your own request variant, the cache keyed the input; require a *different* cache-key request from a second session to receive it.
- Edge-generated `400`/`501` mistaken for the origin's response — verify the status line/body matches the *origin* stack (a bug the edge cannot emit confirms injection; the edge's own error page confirms nothing). WAFs emit their own `403`/`417`-shaped pages; compare `Server`/`Via` banners and error markup before calling upstream.
- Self-only tunnelling counted as smuggling — if only *your* next response is affected, the socket is not shared; require a second session (or a browser-delivered trigger) to be affected.
- Request collapsing mistaken for poisoning — CloudFront and Fastly collapse simultaneous misses for one key and serve the first origin response to all waiters; that is expected behaviour, not corruption. Distinguish by cache key: collapsed requests share a key. In CloudFront logs the first request is `Miss` and the collapsed followers are logged `Hit` — a "hit" in a log is not proof of a stored object.
- Cache-key header matching is substring-based on Cloudflare — a keyed header value of `text/plain` also matches `text/plaintext` and is case-sensitive (`Text/Plain` does not match); a "keyed" header can therefore behave as if it were not keyed for a differently-cased request. Re-test with exact values before concluding.
- Cache rule normalization done by the WAF, not the cache — a `HIT` after an encoded path may be the cache keyed on the decoded form while the origin got the raw path; that is a normalization differential to test, not proof of deception.
- Host-port omission treated as a cache bug when it is a single-request DoS — Kettle found `Host: example.com:1337` absent from the key on Cloudflare and Fastly (Fastly patched, Cloudflare declined at the time, 2020). Do not report DoS-shaped cache-key holes unless the program permits DoS.
- `.js`/`application/json` CDA exception remembered as universal — Cache Deception Armor depends on Origin Cache Control, and an origin `Cache-Control` header or an Edge Cache TTL cache rule can override the protection; re-test per zone instead of assuming the documented exception list applies.
- Internal/app-layer cache poisoning (WP Rocket and similar) mistaken for a normal cached response — indicators are both old and new canaries appearing in one response, canaries on pages you never injected into, and inconsistent hostnames resolving to the same app. Stop, do not spray.

## Version/implementation notes

Connection-reuse model decides which oracle is even available (fingerprint first):

- Per-client keep-alive / connection-locked: only the attacker's own socket is corrupted (tunnelling or connection-locked desync); cross-user impact requires moving the trigger into the victim's browser. Detection: two requests on one connection, the second returning `400` after a `Content-Length`-bearing first request.
- Per-public-IP (IP-locked): affects users sharing the attacker's egress IP; move the attack into the victim's browser so the victim's own connection carries it (an injected `Expect` header on an H2 request can produce an IP-locked desync).
- Shared/coalesced upstream pool: queue poisoning is viable and yields other users' responses — the catastrophic case.
- HTTP/2 connection coalescing lets a client reuse one TLS/QUIC connection for a second origin when the certificate covers both (wildcard/SAN certs), so a desync inside a CDN's own infrastructure can leak responses for unrelated applications on that CDN (observed cross-tenant CDN response capture). A 2026 IETF draft names this "connection contamination": the routing layer picks the backend from a signal fixed at connection setup (SNI/cert) rather than re-validated per request.
- Cloudflare itself had an internal HTTP/1.1 desync (H2 in, H1 internally, H2 upstream) that let one poisoned cache entry redirect unrelated third-party sites (reported via a Heroku-hosted site, patched within hours, ~24M sites exposed, $7,000 bounty).

H2 / H3 front-end → H1 origin translation surfaces (highest yield):

- HTTP/2 front-ends translating to H1 backends (common in Envoy, AWS ALB, CloudFront-to-origin setups) are the highest-yield H2.CL/H2.TE surface; pure H2 end-to-end stacks rarely desync. The H2 front-end uses the frame length; the H1 backend only sees `CL`/`TE`, so the two disagree (H2.CL / H2.TE).
- Frame the whole surface as four length interpretations (the desync research's `CL` / `TE` / `0` (implicit zero) / `H2` (frame length)): each downgrade or translation step adds a pair of interpretations that can disagree, which is why an H2→H1 hop is worse than plain H1 end to end.
- Normative baseline (RFC 9113 §8.2.2): an H2 endpoint MUST NOT generate connection-specific header fields — `Connection`, `Proxy-Connection`, `Keep-Alive`, `Transfer-Encoding`, `Upgrade` — and any message containing them MUST be treated as malformed; `TE` may appear only with the value `trailers`. An intermediary converting H1→H2 MUST remove connection-specific fields or downstream H2 endpoints treat the message as malformed. A front-end that instead *translates and forwards* such a message is the differential.
- Envoy specifics: does not sanitize/escape request properties when generating upstream headers, so illegal characters can be injected into an upstream header value and split the upstream request (GHSA-w5w5-487h-qv8q, fixed 1.25.3/1.24.4/1.23.6/1.22.9; example vector: `%DOWNSTREAM_PEER_URI_SAN%` carrying `\r\n`). It also incorrectly accepts a `200` (not `101`) as a protocol upgrade success, enabling smuggling through Envoy (CVE-2024-23326, GHSA-vcf8-7238-v74c).
- Envoy default header validator (documented knobs that decide desync exposure): HTTP/1 messages with both `Content-Length` and `Transfer-Encoding` are rejected by default, but `allow_chunked_length: true` makes Envoy strip `Content-Length` and process the message — the docs warn this "might lead to request smuggling vulnerabilities"; `skip_path_normalization` and `skip_merging_slashes` (slash merging on by default, not part of the spec) trade path-confusion safety for compatibility; `path_with_escaped_slashes_action` defaults to `KEEP_UNCHANGED` (`%2F`/`%5C`) with `UNESCAPE_AND_FORWARD` explicitly warned as path-confusion-prone; fragments in the path are rejected by default (`strip_fragment_from_path`); `headers_with_underscores_action` defaults to `ALLOW`, which matters where another component treats `_` and `-` as interchangeable; `restrict_http_methods` is off by default, so arbitrary method names are accepted — and normalization rewrites the URI that filters and the upstream see, so a downstream hop can key or route on a different spelling than the client sent.
- H3-to-H1 translation: CVE-2026-48743 — Envoy translates a downstream HTTP/3 request that is complete at the transport layer (HEADERS with FIN) but still carries a nonzero `Content-Length` into an upstream HTTP/1 request with unresolved "body debt"; if the origin replies before reading the declared body and keeps the connection reusable, the next request's bytes are consumed as the first request's body. This is the dangling-byte family expressed through an H3→H1 hop. Fixed in the 1.39.0 line by validating HTTP/3 headers-only request/response content-length and resetting the stream, guarded by `envoy.reloadable_features.quic_validate_headers_only_content_length` (revertable).
- AWS ALB: HTTP Desync Mitigation Mode (powered by the open-source HTTP Desync Guardian) classifies each request; modes are **Defensive**, **Strictest** (origin only sees RFC 7230-compliant requests), and **Monitor**. "Drop Invalid Header Fields" is a separate ALB toggle (`routing.http.drop_invalid_header_fields.enabled`) to strip malformed headers rather than reject them, and AWS now documents it as deprecated for desync mitigation in favour of the desync mitigation mode (`routing.http.desync_mitigation_mode`). Console/metrics: `DesyncMitigationMode_NonCompliant_Request_Count`, plus `classification` / `classification_reason` in access logs.
- ALB + IIS is an unfixed H-V (hidden-visible) discrepancy: a masked `Host`/`Xost` header pair shows ALB returning `400`/`awselb/2.0` while IIS returns `200`/`Microsoft-HTTPAPI/2.0`. AWS chose not to patch it (legacy-client compatibility); the Desync Guardian blocks classic CL.TE, and an H2.TE variant bypassed it before being fixed. Self-mitigation is the two settings above.
- CloudFront always talks HTTP/1.1 to custom origins and its header table decides which triggers even reach the origin: `Connection` is replaced with `Keep-Alive`, `Expect` / `TE` / `Trailer` / `Upgrade` (except WebSocket) / `Proxy-*` / `X-HTTP-Method-Override` / `X-Real-IP` / `X-Forwarded-Proto` are removed, `Transfer-Encoding` and `Content-Length` are forwarded, `User-Agent` is replaced with `Amazon CloudFront`, a `GET` with a body is rejected with `403`, and on the response side `Set-Cookie`, `Trailer`, `Upgrade` are removed while `Transfer-Encoding` is normalized to `chunked`. URL limits: 8,192-byte URL → `414`, oversized headers → `494`, both followed by connection termination.
- Some origins treat `Transfer-Encoding: xchunked` or a folded `Transfer-Encoding : chunked` (space before colon) as absent while the edge strips it — test whitespace and casing variants per hop. A WAF that normalizes TE casing/whitespace before the origin (but not to the same value) is a productive differential.
- CONTINUATION-flood and compression-bomb techniques are denial-of-service shaped and out of scope unless the program explicitly permits DoS testing.

Dangling-byte family (2026 HTTP Terminator):

- The HTTP Terminator (James Kettle / PortSwigger, Aug 2026) autonomously invented new desync triggers, a **dual-matching Content-Length** pattern, and the **dangling-byte** technique that makes response queue poisoning more reliable; it also proposed **Shared-Parser Confusion** and evidence of **response forking**, and produced an Apache Traffic Server zero-day (CVE-2026-63078). Defensive conclusion is unchanged: avoid HTTP/1.1 upstream.
- The Terminator's trigger search space (all reported as viable somewhere) is a useful probe seed list: `GET / HTTP/1.0` + `Transfer-Encoding: gzip`; `Upgrade: websocket`; `CONNECT / HTTP/1.1`; `OPTIONS / HTTP/1.0`; `Expect :\t100-continue` (folded/whitespace variants); `POST / HTTP/2` with no content-length; single-packet attack with `Content-Type: multipart/form-data; boundary=x`; `Content-Type: multipart/byteranges;`; `Transfer_Encoding: chunked`; `Range: ,`; `OPTIONS *?xyz HTTP/1.1`; duplicated `Content-Length: 1`.
- Dangling-byte tolerance varies by server: some frameworks accept `Content-Length: 0` with a body and queue it; others close the connection, which itself is an oracle but not a finding. Convert 0.CL into CL.0 (or a full trap for the victim) with a **double-desync**: a first request poisons the connection with a 0.CL desync, the poisoned connection weaponizes a second request into a CL.0 desync, and the resulting prefix poisons the victim's request.
- Dual-matching `Content-Length`: the HTTP Terminator found that **more than one** `Content-Length` header can be accepted in a way that still produces a desync — test header *count* and duplicate-value variants, not only casing/whitespace mutations.

Per-vendor cache-key and normalization behavior (fingerprint with two canaries before concluding):

| Edge | Default key | Path normalization before cache rules | Notable handling |
| --- | --- | --- | --- |
| Cloudflare | full URL (scheme/host/path+query) + `Origin` + method-override + routing headers | no (raw path) | `Ignore Query String` / `Sort query string` levels; CDA optional per cache rule; URL normalization separate rules-stage feature |
| Fastly | `req.url` + `req.http.host` + `req.vcl.generation`; method ignored | no (path kept raw) | `req.url` unnormalized, host lower-cased; `vcl_hash` overridable; `Fastly-No-Shield: 1` test switch |

- Cloudflare default cache key includes the full URL (scheme, host, path *with* query string), the client `Origin` header (for CORS), the method-override headers (`x-http-method-override`, `x-http-method`, `x-method-override`), and the routing headers `x-forwarded-host`, `x-host`, `x-forwarded-scheme` (unless its value is `http` or `https`), `x-original-url`, `x-rewrite-url`, and `forwarded`. Because those routing headers are keyed by default, changing them busts the cache — so the useful unkeyed inputs sit elsewhere. A custom cache key can add/exclude query parameters, cookies, headers (`accept`, `accept-language`, `referer`, `user-agent`, and similar with case-sensitive substring matching) and user features (`device_type`, `geo`, `lang`), but cannot key `connection`, `content-length`, `cache-control`, `range`, `upgrade`, `if-*`, `host`, `cookie` (use the cookie feature) or `cf-*`; `Origin` stays keyed unless explicitly excluded. Available on all plans: Ignore Query String, Sort Query String, Cache Deception Armor; Enterprise only: query/header/cookie/host/user key components.
- Cloudflare `$scheme` semantics differ by key type: in the **default** key it is the origin scheme (change the zone SSL mode from Flexible to Full and the key changes, forcing a cache bust), while in a **custom** key it is the visitor's scheme unless the origin scheme was explicitly included. Useful when an SSL-mode migration explains a sudden drop in hit rate, and when testing whether `http://` and `https://` requests share one entry.
- Cloudflare limitation that looks like a poisoning bug: Prefetch always uses the default cache key while Cache Rules populate entries under the custom key, so a prefetch and a normal request can disagree on the key even when nothing is vulnerable.
- Cloudflare key-template rationale is also the attack rationale: you "fragment" the cache by adding components and "consolidate" it by removing them — the documented example is dropping the default `Origin` component so different requests share one entry. Any consolidation is a candidate poisoning precondition; check what the deployment actually removed before hunting exotic unkeyed headers.
- Cloudflare `Cache Level: Ignore Query String` keys all requests for a path to one entry (query excluded), which is the unkeyed-query-string precondition; `Sort query string` normalizes parameter order into the key.
- Cloudflare URL normalization is a rules-stage feature: `RFC 3986` normalization percent-decodes unreserved characters (`a-z A-Z 0-9 - . _ ~`), re-encodes other bytes, upper-cases percent encodings, and removes dot-segments; `Cloudflare normalization` additionally converts backslashes to slashes and merges consecutive slashes, then runs RFC 3986. Baseline normalizations (e.g. merging `//`) always apply even with the feature off, and Cloudflare recommends enabling "Normalize URLs to origin" alongside it specifically to avoid cache poisoning. Separately, Cloudflare's *cache rules* are evaluated on the raw path (no path normalization before rule matching), and Origin Cache Control governs whether origin `Cache-Control`/`Set-Cookie` vetoes caching.
- Cloudflare Cache Deception Armor keys on URL extension vs returned `Content-Type` and refuses to cache a mismatch, but it depends on Origin Cache Control (an origin `Cache-Control` header or an Edge Cache TTL cache rule can override the protection) and has undocumented exceptions (e.g. `.js` served as `application/json`; documented exceptions include `application/octet-stream` for any extension, `.jpg` served as `image/webp`, `.gif` served as `video/webm`).
- Cloudflare's default cacheable set is extension-based (not MIME): 7Z AVI AVIF APK BIN BMP BZ2 CLASS CSS CSV DOC DOCX DMG EJS EOT EPS EXE FLAC GIF GZ ICO ISO JAR JPG JPEG JS MID MIDI MKV MP3 MP4 OGG OTF PDF PICT PLS PNG PPT PPTX PS RAR SVG SVGZ SWF TAR TIF TIFF TTF WEBM WEBP WOFF WOFF2 XLS XLSX ZIP ZST, plus `robots.txt`; HTML and JSON are not cached by default. A response with `Set-Cookie`, a non-`GET` request, or `Cache-Control: private|no-store|no-cache|max-age=0` is not cached; without explicit headers, default TTLs are 120m (200/206/301), 20m (302/303), 3m (404/410).
- Fastly's default cache key is `req.url` + `req.http.host` (plus an internal purging variable, `req.vcl.generation`); it ignores the HTTP method by default, so a `POST` and `GET` to the same URL share the object. `req.http.host` is lower-cased before `vcl_recv`, but `req.url` is **not** normalized (capitalisation and encoding are preserved), and TLS vs cleartext requests share the same object. VCL can redefine the key in `vcl_hash` (only legal return: `return(hash)`); Fastly's own guidance prefers `Vary` variations over key rewriting and warns that changing the key risks caching across security domains or enabling cache poisoning — so VCL-injected keys are a differential to test.
- Akamai caches by default on the entire resource path plus the query string; the "Cache Key Query Parameters" behavior (and API Definitions, which override Property Manager) can include all parameters (preserving request order **or** reordering alphabetically), include only specified parameters (prefix matching, case-sensitive per the request URL), or exclude specified parameters — a partial key leaves the omitted parameters unkeyed. Exact Match toggles whether a parameter name must match the whole token. Cache ID Modification adds client-sent headers, cookies, query parameters or a user-defined variable to the key; hostname and path are always keyed, headers injected by edge behaviours are not usable as key inputs, and if an edge behaviour rewrites a client header that is in the key, Akamai still keys on the **original client-sent value** — a built-in cache-key-vs-origin differential to test.
- Akamai rule-tree precedence: a Cache ID Modification in a nested rule **overrides** any instance in a parent or previously executing sibling rule (later nested behaviours replace earlier ones rather than merging), so a key that looks uniform across a property can change per path.
- Akamai POST caching (`cachePost`) is off by default but when enabled has its own key-build options: `useBody: IGNORE` keys POSTs on the URL alone (one stored POST response serves every future POST to that URL), `MD5` adds a digest of the body as a query parameter, and `QUERY` appends the raw body only for `application/x-www-form-urlencoded` — the natural pairing with `cacheId` to define which parameters matter.
- Cloudflare Host key semantics matter for origin routing: with **Use original host** the key and the origin request carry the client `Host`; with **Resolved host** the key uses the host resolved to the origin IP while the forwarded `Host` can differ (e.g. after an Origin Rule) — a request can therefore be keyed under one hostname and served by another origin.
- CloudFront forwards several legacy/unkeyed headers to the origin unless configured otherwise (`Request-Range`, `Max-Forwards`, `From`, `Warning`, `Content-MD5`, `Via`); `Request-Range` is an obsolete range header some origins honour, so it is a candidate for behaviour the cache never keyed.
- Akamai Ghost (the CDN's in-path stack) had CVE-2025-32094: an HTTP/1.x `OPTIONS` request with `Expect: 100-continue` plus obsolete line folding made two in-path Akamai servers disagree, allowing a second request to be smuggled in the first request's body (affects Akamai Ghost before 2025-03-26; CWE-444).
- CloudFront cache key depends on the attached cache policy. The **CachingOptimized** managed policy (ID `658327ea-f89d-4fab-a63d-7e88639e58f6`) includes **no query strings, no cookies**, and only the normalized `Accept-Encoding`; two URLs differing only by query string share one cache entry. **CachingOptimizedForUncompressedObjects** (`b2884449-e4de-46a7-ac36-70bc7f1ddd6d`) is the same with compression disabled. **Amplify** (`2e54312d-136d-493c-8eb9-b001f22f67d2`) includes `Authorization`, `CloudFront-Viewer-Country`, `Host`, all cookies, and all query strings. `UseOriginCacheControlHeaders` (`83da9c7e-98b4-4e11-a168-04f0df8e2c65`) includes `Host`, `Origin`, `X-HTTP-Method-Override`, `X-HTTP-Method`, `X-Method-Override` and all cookies but no query strings; `UseOriginCacheControlHeaders-QueryStrings` (`4cc15a8a-d715-48a4-82b8-cc0b614638fe`) adds all query strings. **Critically, any managed policy with Minimum TTL > 0 caches even when the origin sends `Cache-Control: no-cache`, `no-store`, or `private`** — the classic cache-deception precondition. CloudFront also treats `*` in header/cookie/query names as a literal string, not a wildcard.
- CloudFront separates the **cache key** (cache policy) from what is **forwarded to the origin** (origin request policy): a header or query parameter can reach the origin without being keyed, or be keyed but not forwarded. Test both directions — the forwards-but-not-keyed case is the poisoning precondition, and the keyed-but-not-forwarded case causes origin-side auth/route confusion.
- Fastly nuance for false positives: `hit-for-pass` is a stored marker for a known-uncacheable object, so repeated requests bypass the cache by design; a `pass` response is never stored. Confirm you are not reading a hit-for-pass before calling a `MISS` "no caching".
- Cloudflare enablement paths worth quoting in a report: Cache Deception Armor is turned on inside a Cache Rule (**Cache Rules → Create rule → Then: Cache eligibility = Eligible for cache → Cache Key setting → toggle Cache deception armor**), not a zone-wide toggle; a custom Cache Key is the same Cache Key setting (Query String / Headers / Cookie / Host / User features).
- Param Miner flag detail for cache-key work: **Add cachebuster** (static values) plus **Include cachebusters in headers** applies header-based busters to all Burp traffic, and the scanner probes unlinked parameters for cache-key membership — the combination is what defeats an unkeyed-query-string target that otherwise looks static to every scan.
- The HTTP Terminator's strongest concurrency primitive is the single-packet attack, which removes network jitter from RQP race timing; its anomaly layer also flagged responses with a suspicious text/binary blend (leaked memory, `\0` runs) — the same signal is worth watching manually when a stack mis-parses a body.
- CloudFront `CachingDisabled` (`4135ea2d-6df8-44a3-9df3-4b5a84be39ad`) is the policy that guarantees nothing is stored — use it to prove an edge is not caching before blaming a cache for unexplained responses.

- CloudFront normalization and header hygiene (per the request/response behaviour table): the viewer-facing protocol can be H2/H3 but origin requests are HTTP/1.1; `GET` with a body is refused; `Host` is set to the origin domain; `Connection` is rewritten to `Keep-Alive`; `Transfer-Encoding` is forwarded to the origin and normalized to `chunked` on responses; range requests are forwarded by default; `Vary: *` at Minimum TTL 0 makes every request revalidate; a response whose `Content-Length` disagrees with the body is not cached, and a dropped connection with no `Content-Length` can cache a partial object.
- CloudFront `100 Continue` handling: the origin may send at most **one** `100-Continue` to CloudFront; after that CloudFront expects `200 OK` and errors on a second `100 Continue` — an Expect-based over-read trigger that relies on a second interim response will fail on this hop.
- CloudFront request hygiene for forwarded-header testing: it appends the viewer IP to any client-supplied `X-Forwarded-For` (leftmost values are attacker-controlled; only the last CloudFront-appended value is trustworthy), stamps `X-Amz-Cf-Id`, replaces `User-Agent: Amazon CloudFront`, and caps requests at 32,768 bytes (URL 8,192 bytes → `414`; header overflow → `494`, connection closed). Max cacheable object: 50 GB.
- Cache deception path/delimiter tricks vary with the framework: the URI RFC is permissive, so the cache and origin disagree on delimiters (`;`, encoded `%2f`, trailing `.css`, `?`-in-path). Test per vendor: `;` and encoded delimiters against Cloudflare/Akamai/Varnish front-ends, path vs query handling against Fastly/CloudFront policies.
- Nginx is the highest-yield header-injection front-end: `proxy_pass ...$uri` and `return 302 ...$uri` url-decode the path (so `%0d%0a` becomes a real boundary upstream); the fix is to stop using `$uri`/`$document_uri` in those directives, and the same misconfiguration recurs in OpenResty and Tengine. Permanent fix on both sides: enable HTTP/2 on the upstream connection.

### Hop-by-hop header handling

- RFC 9110 §7.6.1 is the normative removal rule: an intermediary MUST parse `Connection` before forwarding, and for each connection-option MUST remove any field with that name from the message, then remove (or replace) the `Connection` field itself. The RFC's non-exhaustive "known to require removal" list is `Proxy-Connection`, `Keep-Alive`, `TE`, `Transfer-Encoding`, `Upgrade`; a sender MUST NOT use an end-to-end field (e.g. `Cache-Control`) as a connection option.
- RFC 9112 §6.1 framing rules to hold each hop to: a sender MUST NOT send `Content-Length` in a message that contains `Transfer-Encoding`; `Transfer-Encoding` overrides `Content-Length`; a server MAY reject a request with both, but MUST close the connection after responding to one — so a hop that keeps such a connection alive is the anomaly. A server also MUST NOT send `Transfer-Encoding` on a 1xx or 204 response, so a `Transfer-Encoding` header appearing on an interim response is an injected or mis-forwarded field, not legitimate framing.
- RFC 9112 §3 warns that lenient request-line parsing (treating HTAB/VT/FF/bare CR as separators) "can result in request smuggling" when multiple recipients interpret robustness differently — whitespace variants are therefore the first probe, not the exotic one.
- Probe direction: `Connection: Transfer-Encoding` on a request that also carries `Content-Length` asks the first hop to delete `TE`; if the next hop then frames on `CL` (or the reverse order), the two hops disagree. Test each hop combination and each option value separately; do not assume all proxies implement the RFC removal.
- Key-presence variants collapse values: Cloudflare can key on the **presence** of a header without its value (`Check presence of`), and Akamai's Include Values = No keys only the cookie/header/query name. Under either setting, every value of that component maps to one entry — a wide poisoning surface that looks correctly keyed during value-based probing.
- CloudFront's table is a concrete hop model: it rewrites `Connection`, drops `TE`/`Trailer`/`Upgrade`/`Expect`, and forwards `Transfer-Encoding`/`Content-Length` — so a `Connection: Transfer-Encoding` request that passes through a *different* intermediary before CloudFront behaves differently than a direct request.
- H2/H3 doors on the same primitive: RFC 9113 §8.2.2 forbids connection-specific fields outright (malformed), while an H1→H2 translator MUST strip them — a translator that forwards `Connection`/`Transfer-Encoding` as ordinary fields creates a hop-by-hop differential across otherwise-clean protocol layers.

### WAF normalization mismatches

- Cloudflare: URL normalization runs before rules that accept a URL input (WAF custom rules, Workers, Access); with the feature off, "Cloudflare forwards the URL to origin in its original form" unless "Normalize URLs to origin" is enabled. So a request can be blocked/allowed on the normalized view while the origin still receives percent-encoded bytes, or the reverse — build the mismatch deliberately and observe both.
- AWS WAF: text transformations (`URL_DECODE`, `HTML_ENTITY_DECODE`, `BASE64_DECODE`, `LOWERCASE`, `CMD_LINE*`, ...) are applied before inspection, in a chosen order, each costing 10 WCUs. They exist because attackers use unusual formatting to bypass matching, but they only change the string the WAF inspects; the protected resource still sees the original value. A rule that matches only after `URL_DECODE` is bypassable wherever the origin decodes differently or not at all.
- Charset mismatch as a WAF blind spot: injecting `Content-Type: text/html;charset=ISO-2022-JP` let a reflected payload (including an XSS through a response-header-injection path) pass WAF inspection and still execute in the browser (observed against a Cloudflare-fronted Nginx/`Location` retrofit).
- Unicode/encoding normalization is the durable bypass family: the CRLF-powered desync paper points at "Lost in Translation: exploiting Unicode Normalization" (Barnett & Barnett, BlackHat USA) for defeating `%0d%0a` filters — treat every filter that decodes before matching as a candidate for a decoding-order differential.
- Test rule: for every WAF decision that depends on URL/body encoding, replay the same logical request in the raw and encoded form from an origin-visible channel (a reflected parameter or second hop) to see which form the origin actually parsed.

### Cache-deception delimiter / extension tricks per vendor

- The bug is a path-boundary disagreement: the cache keys (and caches) on the extension-bearing path, while the origin strips or ignores the suffix and serves the dynamic page. Candidate delimiters to try per front-end: `;` (`/account;.css`), encoded `%2f` / `%2e` / `%00`, `#`, `?`, a trailing dot, a trailing slash, and dot-segments (`..%2f`). The URI RFC is permissive, so the cache and framework disagree on where the path ends.
- Three cache-rule classes carry deception (Gotta cache 'em all, Doyhenard 2024): **static-extension** rules (path ends in a known extension — each vendor has its own list), **static-directory** rules (everything under a configured prefix is immutable), and **static-file** rules (exact filenames such as `robots.txt`, `favicon.ico`, `index.html`). The exploit shape differs per class: `/Dynamic<Delimiter><Encoded_Dot_Segment><Static_Directory>` when the cache normalizes dot-segments before rule matching, and `/Static_Directory<Encoded_Dot_Segment><Dynamic>` when the origin normalizes but the cache does not.
- Normalization-before-cache-rules differs by vendor: **Amazon CloudFront, Microsoft Azure and Imperva normalize the path before evaluating cache rules by default; Cloudflare, Google Cloud and Fastly do not.** Where the origin normalizes (Nginx, IIS, OpenLiteSpeed) and the cache does not, any static-directory rule can be exploited with an encoded dot-segment.
- IIS backslash note: encoded-backslash handling is a known IIS-vs-cache normalization gap (IIS treats `\` as a path separator; the tested CDNs did not recognize the transformation) — test `%5c` in both directions against IIS origins.
- Browser constraint: the deception payload must survive the browser unrewritten, so only characters the browser will not encode can be delivered via a link; `#` is a fragment that browsers never send (only usable where a proxy/cache treats it as a delimiter), and `%2f`-style payloads depend on the cache decoding before keying.
- Cloudflare: Cache Deception Armor refuses to cache when the URL extension does not match the returned `Content-Type`, but only for its documented/undocumented exception set (`application/octet-stream` for any extension, `.jpg`→`image/webp`, `.gif`→`video/webm`, and the undocumented `.js`→`application/json`). Where CDA is off, plain `;.css` / `.css` tricks apply.
- Fastly/Varnish: URL path and query are both in the default key; test delimiter variants against the VCL-backed front-end and the origin framework's routing together.
- Akamai: caches on the entire path plus query string by default; test `;`-delimited and encoded-dot variants against the origin's routing (Property Manager can also make the key ignore parts of the query string).
- CloudFront: whether a deception caches depends entirely on the attached cache policy — `CachingOptimized` (no query strings, no cookies, Min TTL 1 s) is the classic deception cache for extension-suffixed paths.
- CDA-bypass oracle (Cloudflare): request the extension-decorated URL and compare the stored response's `Content-Type` with the extension; if a dynamic (HTML/JSON) body is served `HIT` from a path ending `.css`/`.jpg`, either Cache Deception Armor is off for that rule, an Edge Cache TTL rule overrode it, or the origin's own `Cache-Control` made it cacheable — record which control was absent before claiming deception.
- Cloudflare deception mechanism to state precisely in a report: caching decisions are **extension-based, not MIME-based** ("The Cloudflare CDN does not cache HTML or JSON by default"), so an HTML response served at a path ending in `.css`/`.js`/`.jpg` is cacheable *because of the path*, while Cache Deception Armor is the only thing that would compare extension to `Content-Type` and refuse it.
- Detection method (same paper): pick a non-cacheable request (`POST`, or `Cache-Control: no-store|private`) as R0; append a random suffix (R1 — identical means you are on an endpoint handler, so move on); then insert each candidate delimiter before the suffix (R2 == R0 means the character is a delimiter for the origin). Repeat with encoded variants, and run the same three-step test against a *static* request/response pair to find the cache's delimiter set. Burp Intruder over all ASCII plus encoded forms is the intended workflow.
- Mitigation the paper gives (useful as a triage yardstick): mark dynamic responses `Cache-Control: no-store, private`, verify cache rules cannot override that header, and ensure the cache key is **not** normalized and that any suffix after a cache delimiter never reaches the origin.
- Defaults are not the deployment: Cloudflare and CloudFront can be configured to apply custom transformations and decode the path for caching or access control, so confirm the property's transformations (Cache Rules, origin request policies, `path_with_escaped_slashes_action`) before assuming vendor-default parsing.
- Rehearse before hunting: PortSwigger ships free labs for the exploit classes (0.CL request smuggling, response queue poisoning, request tunnelling, cache poisoning, cache deception), plus HTTP Request Smuggler 3.0 and the `0cl-find-offset` Turbo Intruder script from the 2025/2026 papers — run the class in the lab first so a live target only sees the final probe.
- Web Cache Deception Scanner BApp exists to flag misconfigured caches; still confirm the stored *authenticated body*, not just a cacheable error page.

### Web cache poisoning: unkeyed inputs, cloaking and the cache-buster rule

- Unkeyed inputs to sweep (Param Miner's "Guess headers" automates it): `X-Forwarded-Host`, `X-Host`, `X-Forwarded-Scheme`, `X-Forwarded-Server`, `X-Original-URL`, `X-Rewrite-URL`, `X-HTTP-Method-Override`, `X-HTTP-Method`, `X-Method-Override`, `Accept`, `Accept-Language`, unkeyed cookies, and unkeyed query parameters (where a policy excludes them).
- Cache oracle first: find a cacheable endpoint with a hit/miss signal (`CF-Cache-Status`, `Age`, `X-Cache`, timing, or reflected dynamic content) and, ideally, one that reflects the URL and a query parameter. Then ask it structural questions: is the port in the key, is the whole query string in the key, is a specific parameter excluded, is the method in the key, is the body in the key.
- Unkeyed query string is the highest-value, lowest-visibility case: changing a parameter value produces no response difference, and even adding a cache-buster parameter does not bust the entry — dynamic pages look static and scanners see nothing. Pierce it with cache-busters in headers that *are* keyed (`Origin` on Cloudflare, `Accept-Encoding`, `Accept`, `Cookie`) or with path variants; `PURGE`/`FASTLYPURGE` may exist unauthenticated (use with care — live-cache hazard). The concrete header busters from the entanglement research: `Accept-Encoding: gzip, deflate, <rand>`, `Accept: */*, text/<rand>`, `Cookie: <rand>=1`, `Origin: https://<rand>.example.com`.
- Masked-`Content-Length` probing descends from Thacher's "Practical HTTP Header Smuggling" (Black Hat Europe 2021) and is implemented as HTTP Request Smuggler 3.0's CL-based analysis: it mutates one header at a time (leading space, space before the colon, duplicate name, invalid value) and compares responses — a cheap, WAF-friendly detector that works where timeout-based probing no longer does.
- Cache parameter cloaking: when one parameter is deliberately excluded, parsing quirks let you hide arbitrary parameters behind it — Varnish regex removal (`?_=[^&]+&`), Rails `;` parameter separator (`?callback=legit&utm_content=x;callback=alert(1)//`), and Akamai's `akamai-transform` exclusion with its `?x=1?akamai-transform=…` quirk (patched after the 2020 report).
- Cache-key delimiter collisions: when the cache builds the key by concatenating components without escaping, two semantically different requests can produce one key — e.g. Akamai's `cid=x=2__Origin='-alert(1)-'` collision let an `Origin`-header XSS become reachable by URL. Cloudflare's documented default key `${header:origin}::${scheme}://${host_header}${uri}` was wrong at the time; Cloudflare acknowledged a theoretical collision and patched by escaping delimiters.
- Fat `GET` requests (a body on `GET`) are a poisoning vector where the origin accepts them; Varnish's builtin VCL strips the body, Rack::Cache and (historically) all Cloudflare systems forward it without keying it. Keep `GET`/`HEAD`/`OPTIONS` bodyless by policy.
- Method not in the key: replaying a `POST` body as a `GET` (or vice versa) can poison the cached `GET` — some caches (Varnish without builtin snippets, and others) omit the method.
- Always attach a unique cache buster while probing unkeyed inputs on a live target, or you will poison real users' entries — the academy guidance flags this as an operational hazard. Prefer the `dontpoisoneveryone`-style parameter, and only remove it when launching the real attack.
- Eliciting a harmful response is only half the job; whether it gets *cached* depends on file extension, content type, route, status code, and response headers.
- Note the Cloudflare quirk: because `x-forwarded-host`, `x-original-url`, and the method-override headers are *keyed by default* there, they usually bust the cache — hunt unkeyed inputs elsewhere before concluding poisoning on Cloudflare.
- Application-layer / fragment caches (integrated cache plugins, WP Rocket-class) have no per-URL key: one request can poison every page, including internal-only ones. Indicators: old and new canaries in one response, canaries on pages you never touched, inconsistent hostnames for the same app. Stop and report rather than continuing to probe.
- Cache poisoning pairs with gadgets in three shapes (entanglement methodology): (a) make a reflected XSS effectively stored, (b) turn a query-reflecting JS/CSS subresource into cross-domain code execution, (c) make a browser-unreachable ("unexploitable") vulnerability reachable — encoded XSS, self-XSS, an XSS in a keyed header. Classify the gadget before judging severity.
- Chain poisoning with deception: an "unexploitable" open redirect or self-XSS can be escalated once a path/delimiter discrepancy lets you store that response under a frequently requested key (`/<Backend_Path><Delimiter><Path_Traversal><Poisoned_Path>` for poisoning; `<Delimiter><Encoded_Dot_Segment><Static_Directory>` for deception). Azure is a documented case where the cache normalizes the key and treats `#` as a delimiter — so choose the delimiter set per vendor rather than assuming `#` is client-only.

### HTTP/2 framing and header surfaces

- HTTP/2 forbids the messy H1 constructs, so a front-end that *validates* the method (rather than trusting it) is harder to desync; the residual surface is the H1 request the front-end **generates** for the upstream (see the vendor notes above), which is where `Content-Length`/`Transfer-Encoding` and CRLF injection reappear.
- RFC 9113 §8.2.2 makes the differential explicit: connection-specific fields (`Connection`, `Proxy-Connection`, `Keep-Alive`, `Transfer-Encoding`, `Upgrade`) are prohibited in H2 messages and MUST be treated as malformed; `TE` is allowed only as `trailers`. A gateway that instead translates them into an H1 upstream request is the bug.
- CRLF can be smuggled inside HTTP/2 header values; a front-end that copies a header value into the upstream H1 request can turn that value into a request boundary (CRLF-powered desync through an H2 front-end).
- CONTINUATION-flood / endless-continuation DoS is protocol-shaped: Apache fixed CVE-2024-27316 in 2.4.59 ("endless continuation frames"); Node.js fixed CVE-2024-27983 in the April-2024 releases. Out of scope unless the program permits DoS.
- h2c (cleartext HTTP/2 upgrade) and pseudo-header handling (`:method`, `:path`, `:authority`, duplicate `:authority`) are additional translation differentials to fingerprint on internal-facing front-ends.
- HTTP/3 / QUIC: 0-RTT early data is replayable by design (the server must deduplicate), connection migration lets a client change IP mid-connection (defeating IP-based defences), and `421 Misdirected Request` is the intended signal for a coalesced request a server is not authoritative for — a server that ignores it is a coalescing/contamination candidate (RFC 9114).
- Envoy's default validator normalizes URI paths per RFC 3986 *without* case normalization and merges adjacent slashes by default (a non-spec behaviour), so two spellings of one path can produce one upstream request while a second hop keys or routes on the literal form.

### Detection methodology and raw-framing notes

- Two detection strategies for an H1 ambiguity: the **timeout technique** (CL.TE — the front-end waits for the body the origin already consumed) and the **differential-response technique** (TE.CL — the origin consumes fewer bytes, so the next request returns the poisoned response). Match the probe to the suspected direction.
- Masked-header differential scanning (Request Smuggler 3.0 pattern) is the most durable detector: permute one header (`Host`, `Content-Length`, `Transfer-Encoding`) with a leading space, folded value, duplicate name, or an invalid value; a response the clean request cannot produce proves a parser discrepancy, and the observation direction picks the exploit class. The timeout technique is now heavily WAF-fingerprinted, so prefer CL.0-class probes where possible.
- Prefer raw TCP tooling (a socket you control, `socat`/`nc`-style, or Burp Repeater on a non-TLS port) so you can see exactly where the front-end puts the boundary; TLS hides the framing, so over TLS rely on timing and response-contamination oracles rather than eyeballing bytes.
- Send a `Connection: close` variant beside a `Connection: keep-alive` variant: a desync that only appears on keep-alive confirms connection reuse is the precondition; a desync that appears even on close is a different (pipeline/parse) bug.
- The HTTP Request Smuggler Burp extension automates the timeout-based detection; treat its hits as hypotheses and confirm with a second oracle (queue contamination or a canary session).
- An unexplained `400 Bad Request` on a request that normally succeeds is a desync smell (Request Smuggler labels these "Mystery 400"); the 0.CL research found that many such responses were exploitable once an early-response gadget was paired with them.
- Cloud WAFs and web VPNs are disproportionality productive front-ends: 0.CL findings clustered on sites using a cloud WAF (a WAF introducing the parser discrepancy it was meant to block), and Kettle advises against placing a web VPN behind any reverse proxy at all.
- RQP is a volume game, not a single-packet demo: the reported GitLab case needed ~27,000 requests to win the race, and the CRLF case study ran 500 connections for 20+ minutes before internal tokens appeared. Budget accordingly, keep rate limits polite, and report the oracle plus one captured non-attributable sample rather than continuing to harvest data.
- Reverse desync trigger shape to carry: `GET /%0d%0aContent-Length:%200%0d%0a%0d%0a` (or a `return 302 $uri` variant) produces a second response on the origin socket; it only survives where the browser/edge tolerates the extra bytes — the stacked-response problem is what usually kills it.
- Drop a constant cache-buster (in a keyed header) on every probe against a live cache, and use `Connection: close` when you do not intend to reuse the socket — both limit collateral poisoning.

### Vary and cache-key mechanics

- `Vary` splits the cache by the listed headers. If a response reflects an attacker-influenced value *and* the origin doesn't `Vary` on the header that carried it while the cache does (or vice versa), the two disagree on object identity — a poisoning primitive.
- Query-string normalization differential: some caches normalize parameter order, drop tracking parameters (`utm_*`), or re-encode values while the origin keys on the literal string (or the reverse). A cache that normalizes to a canonical URL your victim also requests lets you poison the canonical entry from a non-canonical request. Akamai's "reorder alphabetically" cache-key option and Cloudflare's "Sort query string" are first-class examples of key normalization to test.
- Cookie keying differs: a cache that ignores cookies entirely (CloudFront `CachingOptimized` includes none) will serve a session-influenced response to everyone; a cache that keys all cookies (CloudFront `Amplify`) won't. Fingerprint which cookies are keyed before a cookie-based poison or deception.
- Fastly recommends `Vary` over `vcl_hash` rewriting for language/geo/login variations and caps the number of variations; CloudFront also rewrites/removes `Vary` values it does not support (`Vary: *` revalidation behaviour depends on Minimum TTL). Treat "which side owns variation" as a design gap to test, not an implementation detail.

### Origin/backend behaviors to fingerprint

- Node.js origin: older versions are a common desync origin behind a translation proxy — CVE-2024-27983 (HTTP/2 CONTINUATION) and CVE-2024-27982 (smuggling) were fixed in the April-2024 releases.
- Apache httpd origin: response-splitting/desync hardening and the CVE-2024-27316 endless-CONTINUATION fix landed in 2.4.59; older builds are a candidate. Kettle never found a working early-response gadget on Apache in default config — it is "too studious about closing the connection when it hits an error" — but `OPTIONS *?xyz` worked as an early-response gadget on a non-default Apache target.
- Apache Traffic Server: carry the CVE-2026-63078 trigger in the probe set and fingerprint `Server: ATS`; a `TRACE`/`DELETE` pair visible in one response is the Terminator's observed contamination shape.
- Microsoft IIS: `/con` (and the reserved device names `CON, PRN, AUX, NUL, COM1…`) forces an early response without waiting for the body and leaves the connection open — the canonical 0.CL early-response gadget; IIS also carries the unfixed ALB H-V discrepancy.
- Frameworks differ on terminating a body: some accept `Content-Length: 0` *with* a body and queue it (dangling-byte tolerant), others close the connection (an oracle, not a finding).
- H1-upstream-only deployments are the root cause: the durable fix everywhere in this pack is to stop speaking HTTP/1.1 upstream (H2/H3 upstream removes the translation differential). Vendors with upstream HTTP/2 at the time of the 2025 desync research: HAProxy, F5 BIG-IP, Google Cloud, Imperva, Apache (experimental) and Cloudflare (uses HTTP/1 internally anyway); without upstream HTTP/2: Nginx, Akamai, CloudFront, Fastly.
