# API / Protocol Research

> SCOPE: Load when the target exposes REST, GraphQL, gRPC, SSE, WebTransport, or a BFF/gateway fronting internal services.

## Research families

- REST version drift and legacy or internal routes
- Method override and content-type or parameter precedence
- Undocumented client-reachable routes mined from shipped clients
- GraphQL introspection, batching, aliasing, depth, and persisted-query boundaries
- GraphQL mutation versus query authorization differentials
- GraphQL subscription authorization (handshake-only vs per-operation)
- GraphQL field-level authorization drift (federation directives, entity resolvers, `@include`/`@skip`)
- GraphQL schema/SDL disclosure outside introspection (federation helper fields, error metadata, shipped maps)
- gRPC reflection, metadata auth, stream authorization, and protobuf edge cases
- gRPC-Web proxy translation gaps (metadata strip/downcase/inject)
- gRPC-JSON transcoding: REST view of a gRPC service with uneven authz
- GraphQL-over-HTTP verb and content-type enforcement (`GET`/`POST`, JSON vs `x-www-form-urlencoded`)
- SSE subscription, isolation, and reconnection behavior
- WebTransport and QUIC datagram or stream channel boundaries
- BFF and gateway-to-origin translation differentials
- BFF/token-handler session-vs-token boundary (what the browser can reach)
- BFF outbound-request shaping (client-controlled destination host/path with a server-held token)
- REST/GraphQL/gRPC views of the same object disagreeing on authorization
- API key scope and restriction drift (API-level restrictions, application restrictions, key reuse across surfaces)
- Pagination cursor and continuation-token scoping (cursor IDOR, replayed tokens, count leakage)
- Persisted-query stores: safelist enforced versus APQ treated as if it were one
- Mass-assignment and hidden-parameter acceptance on API writes (field-level detail in access-auth pack)
- Webhook and callback registration as an SSRF-adjacent primitive (delivery URL fetched server-side)

## Preconditions

- More than one representation of the same capability exists (v1/v2, REST/GraphQL, gateway/origin, web/mobile) and authorization may have been applied unevenly.
- Client-shipped artifacts (JS bundles, mobile apps, manifests, OpenAPI docs) reveal routes the crawlable surface hides.
- For GraphQL abuse: batching, aliasing, persisted queries, or subscriptions enabled; introspection disabled is not equivalent to schema hidden (error messages leak it). Apollo Server disables introspection by itself when `NODE_ENV=production`, so "introspection is off" is a default, not evidence of hardening — the differential is whether schema-shaped errors still resolve fields.
- For GraphQL CSRF: the endpoint accepts `GET` or `application/x-www-form-urlencoded` (the JSON-only content-type assumption is what normally blocks CSRF), or APQ is served over GET.
- For GraphQL federation: a subgraph is reachable without the router (direct host/IP/port), so `_service`/`_entities` are exposed even when the router is hardened.
- For GraphQL field-level drift: authorization directives (`@requiresScopes`, `@authenticated`, `@policy`) live in the schema and are router-enforced — an older gateway, a non-GraphOS gateway, or a subgraph-only route may not enforce them.
- For gRPC: reflection or a Web proxy (Envoy, grpc-web) exposing the service to HTTP clients; metadata-based auth that may be case- or presence-sensitive.
- For gRPC-Web: a proxy that maps HTTP headers to gRPC metadata (Envoy header-to-metadata filter, grpc-web translation) so a client-controllable header becomes backend metadata.
- For gRPC-JSON transcoding: a transcoding layer (Envoy `grpc_json_transcoder` or grpc-gateway) that maps HTTP into RPC; the backend sees `POST /<pkg>.<Service>/<Method>` regardless of the client's verb and path, so method-based controls keyed on the original verb are the seam.
- For SSE: `EventSource` transport constraints (cookies yes, custom headers no) forcing weaker auth than the REST equivalent; `Last-Event-ID` accepted on reconnect; single-connection SSE modes that carry a reservation token in the URL.
- For WebTransport: HTTPS with an explicit port; the session request is sent with credentials mode `omit`, so cookie-session identity does not ride the handshake — identity arrives via the `headers` option or a separate authenticated bootstrap, then is assumed for the multiplexed session.
- For gateway bypass: a directly reachable origin (IP, alternate host, port) or a header the gateway trusts from the client (`X-Forwarded-For`, `X-Original-URL`).
- For BFF: the browser holds only a session cookie, but the BFF injects identity/scope headers upstream — those injected headers are the trust seam; the BFF also chooses the upstream host per request, and the upstream receives the user's token.
- For method/precedence issues: a gateway or framework that normalizes method, path, or content-type differently from the backend handler behind it; more than one hop implements its own method-override or path-fallback.
- For API key issues: keys exist in more than one surface (public API, internal service, mobile, browser) with different restriction sets, or keys are accepted as a query parameter / are embedded in shipped clients.
- For pagination issues: list responses carry a cursor, page token, or continuation token that the server does not re-bind to the requesting principal, or that leaks collection size.
- For REST versioning without URL versions: the credential pins the version (Stripe-style), so both versions share one endpoint and one path; you need two credentials pinned to different versions, or a per-request version override, to produce the differential.
- For persisted-query stores: a cache (APQ) is deployed but believed to be a safelist; a real safelist exists but the deployment accepts both hash-only and full-document requests.
- For webhook issues: a registration endpoint accepting researcher-controlled delivery URLs whose fetch behavior (headers, retries, secret inclusion) is observable via collaborator.

## Oracles

- Version differential: deprecated or legacy route (`/v1/`, `/beta/`, `/internal/`) honors an operation the current version rejects, or skips an authorization check the current version enforces.
- Method/precedence differential: `X-HTTP-Method-Override`, body-vs-query parameter, or `Content-Type` switch changes the enforced operation or identity the server acts under.
- Hidden-route reachability: endpoint found only in JS/mobile artifacts responds with non-error behavior for a low-privilege session (compare against a random-path 404 control).
- GraphQL authorization gap: mutation or nested field resolving another user's object succeeds where the REST equivalent returns 403 — verify both directions with two researcher accounts.
- GraphQL field-level drift: a field the router filters (`UNAUTHORIZED_FIELD_OR_TYPE`, `null` + error path) resolves for the same principal through a subgraph route, a second gateway version, or a non-GraphOS gateway; conversely a field denied directly succeeds through federation entity resolution.
- Federation helper-field oracle: `{ _service { sdl } }` returns the subgraph SDL while `__schema` is blocked; `_entities(representations:)` accepts externally supplied entity keys and returns objects the caller could not query directly (impersonating the router).
- Federation coverage oracle: diff the SDLs collected from every reachable subgraph (`_service { sdl }` per host) against the router's public schema to find fields/arguments that exist internally but are not composed into the public graph — those are the fields whose enforcement never got reviewed, and the entities they resolve are the `_entities` targets.
- Batching/aliasing abuse: single batched request performs N auth-guarded operations where N sequential requests are rate-limited or blocked.
- GraphQL CSRF via transport: a state-changing operation completes from a cross-site context when the endpoint accepts the form content-type or serves a GET-carried operation — the CSRF-defence bypass, confirmed by the state change read back.
- APQ trust confusion: on an APQ cache miss the server executes the client-supplied query text (APQ is a cache, not a safelist) — an unregistered query still runs, proving "persisted queries" are not enforced as an allowlist. Compare against a real PQL/safelist deployment, where the same unregistered hash is refused.
- Introspection bypass: `__schema` blocked at the root but `__type(name:)`, field-error "did you mean" suggestions, or a case/whitespace variant still resolves schema — enumerate with a controlled query, not a scanner.
- Directive-reference oracle: with router authorization directives, a field that is excluded with `@include(if: false)` or `@skip(if: true)` still yields an `UNAUTHORIZED_FIELD_OR_TYPE` error — referencing a protected field discloses that it exists and is protected even when you never receive it. Conversely, if introspection is enabled, protected fields stay visible in the schema regardless of filtering.
- APQ-state oracle: `PERSISTED_QUERY_NOT_FOUND` means the hash is absent from the cache (query text may still execute if you send it); `PERSISTED_QUERY_NOT_SUPPORTED` means APQ is disabled entirely; a successful hash-only response for a query you never registered means the entry was persisted by someone else — none of these is a safelist verdict by itself.
- Subscription authorization gap: auth is checked once at `connection_init`/HTTP upgrade, but a subscribe operation referencing another user's topic resolves after the handshake, or a multiplexed connection shares one identity across subscriptions. In SSE single-connection mode, the `PUT` reservation is the step that carries credentials, and each later operation request is bound to the stream only by the reservation token — if the server does not also check per-request credentials, operation authz is inherited from the reservation.
- Subscription identity drift: a long-lived subscription keeps streaming after the underlying token expires/revokes or after the principal's scopes change; the server never re-evaluates authorization for already-open streams.
- gRPC metadata gap: request without (or with emptied, case-varied) `authorization` metadata succeeds; per-message authorization missing on an authorized stream (act as user A on stream, reference user B's object mid-stream).
- gRPC metadata translation gap: a metadata key's case or `-bin` (binary, base64) treatment differs between proxy and backend, so a check that looks for `authorization` misses `Authorization` or `authorization-bin` — or a client header promoted to metadata is trusted. Appended duplicate credentials (grpc-gateway appends rather than overwrites) can make the backend join two values into one decision.
- gRPC-Web query-param metadata: the client "advertises" request metadata as URL query params, and the spec only says the proxy *should* strip them before forwarding — a proxy that does not leaves client-controlled metadata on the backend call.
- Transcoding route/verb differential: the same RPC authorized differently when called as native gRPC versus `POST /<pkg>.<Service>/<Method>` versus the transcoded REST path; the backend sees `x-envoy-original-method`/`x-envoy-original-path` and may trust them.
- SSE isolation failure: subscription to another user's topic/channel streams their events; `Last-Event-ID` replay on reconnect returns events outside the subscriber's scope.
- WebTransport channel gap: a session authenticated once then opens streams/datagrams for a topic the per-stream handler never re-authorizes; server-initiated streams arrive on a session opened under a weaker principal.
- Gateway bypass: origin reached directly (or via `X-Original-URL`/`X-Rewrite-URL`) serves admin or internal responses the gateway denies.
- BFF trust-seam abuse: the upstream honors a client-supplied `X-User-Id`/`X-Email`/`X-Scopes` header that the BFF is supposed to set, so a direct hit on the upstream (or a header-spoofing path through the BFF) impersonates a principal.
- BFF outbound-host abuse: a BFF endpoint takes the upstream destination (host, base URL, or path prefix) from client input and forwards the user's access token to it — observe the token arrive at a researcher-controlled collaborator and compare with the allowlisted-upstream control.
- Transcoding differential: the same method is authorized differently via the gRPC-JSON transcoded REST path and the native gRPC/GraphQL path.
- API key restriction oracles: a key restricted to API A is accepted on API B (missing or bypassed API restriction); an application-restriction check that trusts a client header (`X-Android-Package`, `X-Android-Cert`, `X-Ios-Bundle-Identifier`, `Referer`) is spoofable; a `rk_`-style restricted key executes an operation outside its permission set; a key in a query string appears in logs/Referer.
- Pagination cursor oracles: a cursor, `continue`, or `page` token issued for principal A returns principal B's objects; an opaque cursor is actually an offset/raw ID that can be edited; `remainingItemCount`/`total_count`/`has_more`/`next_page` discloses cross-principal volume; the server accepts a `limit` above its documented maximum.
- Aggregation oracles: count, total, or aggregate endpoints disclosing cross-principal volumes where list endpoints are correctly scoped.
- Webhook fetch confirmation: collaborator receives the server-side delivery with unexpected headers, secrets, or internal source IP — confirms the fetch primitive without touching internal targets.
- Protobuf default-value oracle: a field omitted entirely (proto3 zero) passes a check the same field with a positive value fails — compare omit vs send-zero vs send-value on the same object.
- Streaming Origin gate: a WebSocket/SSE handshake with no `Origin` (or a foreign `Origin`) still authorizes, letting a cross-site page subscribe and read another session's events.

## Minimal safe proof

1. Inventory from evidence: extract routes, versions, and parameter names from shipped JS, mobile traffic, manifests, and error messages — no wordlist spraying against production.
2. Pairwise differentials only: for each candidate, run the same operation through both representations (v1 vs v2, REST vs GraphQL, gateway vs origin, native gRPC vs transcoded REST) with two researcher-owned accounts; record both responses.
3. Read-back over response codes: confirm authorization effects by reading back state as the victim-context account, never by asserting on status codes alone.
4. GraphQL depth/batching: start with depth 3 and batch size 2; stop at the first policy signal (error, throttle) — never run alias-amplified or deeply nested queries that risk backend load.
5. GraphQL CSRF: prove the state change from a cross-site context against your own account only; never trigger a state change on a third-party record.
6. gRPC streams: one stream, two messages maximum for the authz probe; close the stream immediately after observing the authorization decision.
7. gRPC-Web: record which hop (browser → proxy → backend) you tested; a bypass through one proxy may not reproduce on another.
8. Federation probes: build the `_entities` representation from an object *your* account can already see (its own key), then ask for one field you are denied — never construct representations for keys you cannot observe, and never sweep key ranges.
9. Subscription probes: subscribe to exactly one topic/channel per connection, hold it only long enough to observe one event, then close; never subscribe to another tenant's feed and wait for real traffic beyond the single confirming event.
10. API key probes: use a key you own (or one explicitly provided in scope); never rotate, revoke, or exhaust a production key to test a restriction; the confirming signal is a scoped call succeeding where the key's restriction says it must fail.
11. Pagination probes: walk one page past the boundary with your own cursor, then attempt one foreign cursor value; stop the moment a foreign object appears and record only the cursor, never the page body in bulk.
12. Cost-limit stop signals: stop immediately on `COST_ESTIMATED_TOO_EXPENSIVE`, `BATCH_LIMIT_EXCEEDED`, a 429/timeout, or any router message that the operation was rejected for cost — the limit fired, which is a negative result, not something to iterate around.
13. Expired paging/token signals: `410 Gone` on a Kubernetes `continue`, an invalid-token error on a reservation token, or a cursor that the server reports as unknown are expected lifecycle outcomes — restart cleanly rather than retrying with modified tokens.
14. Stop conditions: another user's data returned, state changed in another account, rate-limit or WAF intervention, or origin IP confirmation that would encourage bypass scanning — halt and report the differential.
15. Webhook probes point only at researcher-controlled collaborator endpoints; never register internal, metadata, or third-party URLs as delivery targets.
16. BFF outbound-host probes point only at a collaborator you control; do not send a victim token to any third-party host.

## False positives

- Legacy route returning identical authorization decisions with different response shapes — version drift in format only; require a decision differential.
- Introspection disabled with no field-suggestion leakage and uniform authz — hidden schema alone is not a finding; require an authorization or data failure.
- GraphQL error messages naming fields the requester is still denied — enumeration aid, not access; require data return or mutation effect.
- `__type` reachable but it only echoes type names already public in client bundles — require a field/argument you could not otherwise learn, or an authz failure.
- `_service { sdl }` reachable but the response is the public supergraph SDL already shipped to clients, or the subgraph is network-isolated from the caller — require internal types/fields (or a direct `_entities` data return) you could not otherwise reach.
- Schema introspection "recovers" nothing new because the client bundle already ships the full SDL or generated types — reconstruction that only re-derives the client's own schema is not a finding; require a field, argument, or capability the client could not already use.
- Persisted queries enabled but mutations additionally require a same-site token or POST+`application/json` only — the CSRF path is closed; require the state change to actually complete cross-site.
- APQ present but the deployment also runs a real PQL/trusted-document safelist — rejections of unregistered hashes mean the safelist is real; the finding requires an unregistered query to execute.
- gRPC health-check or reflection endpoint exposing service names without data access — fingerprinting aid; require a metadata or stream authz bypass.
- SSE endpoint reachable without custom headers but enforcing equivalent cookie-session authz with correct isolation, and distinct-connections mode inheriting per-request auth — transport-shaped auth is fine if the decision is equal; require isolation failure.
- `Last-Event-ID` accepted but scoped to the subscriber and validated against their own event log — correct replay semantics; require foreign events.
- WebTransport session with credentials mode `omit` is the spec default, not a bug; require a per-stream authorization failure or a token sent to an unintended party via the `headers` option.
- Gateway trusting `X-Forwarded-For` for logging or rate-bucketing only, with auth decisions made on session — require the header to change an authorization outcome.
- BFF-injected identity headers that the upstream *overwrites* from a verified session (client value ignored) — require the client-supplied value to survive to an authorization decision.
- Undocumented route that 404s, redirects to login, or enforces identical authz — hidden is not vulnerable; require the differential.
- Aggregate or count values that match the requester's own scoped data exactly — correct scoping; require cross-principal inclusion.
- `total_count`/`remainingItemCount` present but computed over the requester's own filtered set — require a value larger than the scoped set, or an enumeration that returns foreign rows.
- Batch endpoint that executes operations atomically with per-item authorization re-checked — require the missing per-item check, not batching alone.
- Subscription whose handshake authenticates but whose resolver also re-authorizes per event — correct; require the post-handshake authorization to be skipped for a non-owned topic.
- Webhook delivery that fires only to allowlisted or verified domains with secret-signed payloads — require the unvalidated fetch or secret leak, not the feature alone.
- gRPC reflection that exposes only first-party descriptors already present in the client bundle — require a service or method you could not otherwise reach, or a metadata bypass.
- Batch/alias limits enforced at the operation-count or cost level (one throttled request for the whole batch) — require the limit to be *bypassed*, not merely the feature to exist.
- Demand control enabled in `measure` mode (costs recorded, nothing rejected) — measuring is not enforcing; check `mode` before claiming a limit does or does not exist.
- Protobuf field omitted but the server treats "missing" as required and rejects the call — require the omitted field to actually change the authorization decision.
- An unrestricted API key is a hygiene signal, not automatically an access bug — require the key to reach data or an operation its intended audience should not have.
- Method override accepted but the outer request is authorized identically to the inner method (no decision change) — require a hop that authorizes the outer form while another executes the inner.
- Error `stacktrace`/`extensions` present but the deployment is not production (`NODE_ENV` unset or `development`) — development-mode verbosity is expected; require a production-shaped deployment or data/schema exposure that survives error filtering.
- `BATCHING_NOT_ENABLED` from a router receiving a batch array — batching is simply off; the oracle needs a deployment where `batching.enabled: true`.
- grpc-gateway stream error details (code/message/details) appearing in JSON chunks — verbose defaults, not an authorization bypass; require details that name internal services or data the caller cannot otherwise reach, and confirm with a non-streaming control.

## Version/implementation notes

### REST — versioning, method override, keys, pagination

- The same resource often exposes several write verbs (`POST` create, `PUT`/`PATCH` update, `DELETE`) and each handler carries its own authorization check; the drift is a verb that forgot the check the create path has. Enumerate verbs per resource, not per endpoint family.
- **Method override** (`X-HTTP-Method-Override`, `_method=`, `method=` body field) is a real feature in many frameworks; when a gateway authorizes on the outer `POST` but the origin dispatches on the overridden method, the enforcement seam opens. Confirm by comparing the effect, not by the header being accepted.
- **Parameter precedence** is per-stack: query string vs body vs cookie vs header for the same key (`id`, `user_id`, `role`). A gateway that validates the query copy while the handler binds the body copy is the classic split. Send the same parameter in two places with different values and observe which one the server acts on.
- **Path normalization**: `/a/../admin`, `%2e%2e`, duplicate slashes, trailing dots/spaces, case-folding, and semicolon path params (`/admin;x=/`) are normalized by different hops at different stages; the bug is a hop that authorizes on the normalized form while the origin routes on the raw form, or vice versa.
- **Method override, per stack** (verified implementations, not folklore):
  - Rack / Rails (`Rack::MethodOverride`): reads `_method` from form or parseable body data, else the `X-HTTP-Method-Override` header; applies **only when the real method is `POST`**; overridable set is the full method list; original method preserved in `rack.methodoverride.original_method`.
  - Laravel (pre-existing pack knowledge, not re-verified this pass): form helper `@method('PUT')` emits a hidden `_method` field; the route dispatcher honors it on `POST`.
  - Spring (`HiddenHttpMethodFilter`): `POST` body parameter `_method` (name configurable via `methodParam`); only `PUT`, `DELETE`, `PATCH` are accepted; must run after multipart processing to see a multipart body parameter.
  - grpc-gateway: `POST` + `X-HTTP-Method-Override: <method>` is honored by default (path-length fallback for HTML forms), and the official docs call out the WAF bypass: a WAF that only allows `POST` sees a POST while the gateway routes to the `DELETE` handler; disable with `WithDisableHTTPMethodOverride`, and separately `WithDisablePathLengthFallback` for the `POST`+`application/x-www-form-urlencoded` → `GET` fallback.
- **Version drift is only a finding when the decision differs** (see Version drift below): same verb, same object, two versions, two outcomes.
- **REST versioning models**: vendor-pinned versions per account (Stripe: an account's API version is fixed until upgraded; major releases may break compatibility, monthly releases are backward-compatible) mean the *same request* returns different fields/validation depending on the credential's pinned version — a differential oracle that needs no `/v1` vs `/v2` path at all. Deprecation is signaled with the `Sunset` response header (RFC 8594) announcing when a URI becomes unresponsive; a resource that still serves after its announced sunset, or whose legacy behavior is still reachable through a lower version, is the drift to test.
- **API key scope models** (the authorization surface behind `X-Api-Key`/`key=`):
  - Google Cloud API keys carry two independent restriction axes: **API restrictions** (which APIs accept the key; an unrestricted key "can be used with all APIs that accept keys generated by Google Cloud") and **application restrictions** (websites/HTTP referrers, IPs, Android apps, iOS apps). Keys created via `gcloud`/REST can be unrestricted (the console forces at least one API restriction), and the official docs state the Android and iOS app restrictions are easily bypassed because they trust client-supplied headers (`X-Android-Package`, `X-Android-Cert`, `X-Ios-Bundle-Identifier`). Programmatic surfaces to check or enumerate: `gcloud services api-keys create --api-target=...`, the `restrictions.apiTargets` field on the REST API, and Cloud Asset Inventory queries over `apikeys.googleapis.com/Key` (e.g. `-resource.data.restrictions.apiTargets:*`) that find keys missing API or application restrictions. HTTP-referrer restrictions support only limited wildcards (a single `*` for a subdomain or path, never mid-URL).
  - Stripe restricted keys (`rk_`) assign per-resource `Read`/`Write`/`None` permissions, unlike full-access secret keys (`sk_`); an insufficient permission yields an invalid-request error whose body names the missing permission, and every Stripe API supports restricted keys. Permission mapping follows the verb: `GET` needs `read`; `POST`/`PUT`/`DELETE` need `write`, and write implies read. A restricted key is still an API key: its value is bearer-only, it is shown once (creation requires 2FA), and the docs recommend it for third parties and AI agents precisely because the alternative is total access — so a `rk_` key found in a client bundle or log is a scope question, not automatically a full compromise.
  - Oracle shape: take a key whose restriction set is known (your own key), call an API outside that set (Google API restriction), an operation outside a `None` resource (Stripe RAK), or a host/surface outside its intended audience, and compare with the in-scope control.
  - Bearer-token transport precedence is a related seam: RFC 6750 defines exactly three places a token may ride (Authorization header, form body `access_token`, URI query `access_token`), says clients MUST NOT use more than one method per request, and warns the URI method leaks via logs/history. Deployments that accept more than one place, or that read the token from a different place for authorization than for logging/rate-limiting, are the ones to probe with conflicting values.
  - Bearer error semantics give a free capability fingerprint: `401 invalid_token` (expired/revoked/malformed) versus `403 insufficient_scope` (the token is valid but under-scoped) versus a bare `401` with no error code (no credentials at all). The distinction matters when a platform silently falls back to an anonymous principal instead of failing.
- **Pagination cursors are capability tokens until the server re-binds them**:
  - Stripe v1 lists use `starting_after`/`ending_before` (mutually exclusive) where the cursor is an **existing object ID**, `limit` 1–100 (default 10), and `has_more`; search endpoints use an opaque `page`/`next_page` cursor and expose `total_count` only on request, accurate only up to 10,000.
  - Kubernetes list paging uses `limit` + a `continue` token; the token survives a short window (about 5 minutes by default), then returns `410 Gone` and the client must restart; continued pages are served from a constant `resourceVersion`, and combining `continue` with an explicit `resourceVersion` is invalid (`400`). `remainingItemCount` is returned in list metadata. Watch/history details: an etcd 3 backing store keeps roughly the last 5 minutes of change history by default, a `watch` can request `BOOKMARK` events with `allowWatchBookmarks=true` to advance its position without receiving objects, and an unavailable history returns `410 Gone` so the client must re-list. On a list, an unset `resourceVersion` means "most recent" while `resourceVersion=0` means "any" — a client that pins consistency by accident gets a different snapshot guarantee than intended. Further consistency controls: `resourceVersionMatch=Exact|NotOlderThan` (invalid without `resourceVersion`) and `sendInitialEvents` requiring `resourceVersionMatch=NotOlderThan`. A paging/consistency parameter that the server silently ignores is itself an oracle (the doc warns clients to handle servers that do not honor `resourceVersionMatch`).
  - Stripe's `/v2` namespace uses a different pagination interface than `/v1`, so a client that speaks v1 pagination against a v2 surface (or a gateway that proxies one to the other) is another version-representation differential.
  - Test the cursor's binding before testing its opacity: a raw object ID cursor can be produced for another principal's object and replayed; an opaque token can be replayed across sessions or across principals; a signed token can still encode an offset.

### GraphQL — persisted queries, APQ, CSRF, batching, subscriptions, introspection

- **APQ is a cache, not a safelist.** Apollo Server APQ caches a query string keyed by its SHA-256 hash: the client sends `extensions.persistedQuery.sha256Hash`; a hash-only request for an unknown query returns error code `PERSISTED_QUERY_NOT_FOUND`; the client then resends the full query text plus the hash, and the server persists it. APQ is enabled by default (`persistedQueries: false` disables it), the cache TTL is deployment-configurable (in-memory default: no TTL), and hashed queries can be sent as `GET` (`useGETForHashedQueries`) for CDN caching. A deployment that *believes* APQ enforces "only known operations" is wrong — arbitrary query text still executes on the first (miss) request.
- **APQ storage is a configurable cache, which is what makes the distinction exploitable.** Apollo Server keeps APQ entries in its default in-memory cache unless a `cache` backend is supplied (or a dedicated `persistedQueries.cache` `KeyValueCache`), and `persistedQueries.ttl` (seconds, or `null` for none) controls eviction. A short TTL or an external cache with eviction means entries disappear and get re-registered by the next client that sends the text — so "the query is in the store" is transient state, not a policy.
- **A real safelist is a PQL / trusted-document list.** Apollo's GraphOS Router (≥ v1.25.0) enforces safelisting by fetching a persisted query list (PQL) from GraphOS and can require clients to send operation IDs instead of full documents. Fingerprint which of the two is configured: with PQL, an unregistered operation is refused even with a valid-looking hash; with APQ, it is executed and then stored.
- **APQ over `GET` reintroduces CSRF only when the server allows it.** The GraphQL-over-HTTP draft says a `GET` carrying a mutation **MUST** be rejected (405 recommended), so the CSRF path exists where the deployment violates that, or where it accepts `application/x-www-form-urlencoded` (a browser-simple request with no preflight). The draft itself warns that alternative media types open CSRF and cites the community `GraphQL-Require-Preflight` custom-header pattern as a mitigation.
- **GET encoding rules for probe construction**: the request parameters (`query`, `operationName`, `variables`, `extensions`) go in the URL query component encoded as `application/x-www-form-urlencoded` (WHATWG `URLSearchParams`); `variables`/`extensions` must each be a JSON string; an empty string for an optional parameter is equivalent to omitting it; `operationName=null` selects an operation literally named `null`, so use an empty value or omit the parameter when you mean "no operation name".
- **The draft's own security note is an argument to cite**: authorization decisions "should not" be made from any part of the GraphQL-over-HTTP request — they belong in the schema during execution, producing partial responses. A deployment that gates at the HTTP layer (method, path, content type, header) while the schema has no field-level checks is exactly the pattern whose gaps this pack hunts. The draft also warns that `multipart/form-data` can reference a large value multiple times, letting a small HTTP request cause a much larger GraphQL operation.
- **Transport enforcement is specified, implementations drift.** The draft requires `POST application/json` support, defines `application/graphql-response+json` as the response media type, recommends `294` for partial success, `405` for GET-mutation and unsupported methods, `415` for unsupported request content types, and `422` for validation failure. Fingerprint what the single endpoint actually accepts rather than assuming.
- **Fingerprint the engine from `extensions.code` before assuming behavior.** Apollo Server's codes are a reliable fingerprint: `GRAPHQL_PARSE_FAILED`, `GRAPHQL_VALIDATION_FAILED`, `BAD_USER_INPUT`, `PERSISTED_QUERY_NOT_FOUND` (hash unknown to the APQ cache), `PERSISTED_QUERY_NOT_SUPPORTED` (APQ disabled server-side), `OPERATION_RESOLUTION_FAILURE` (multiple named operations without `operationName`), `BAD_REQUEST`, `INTERNAL_SERVER_ERROR`. A `PERSISTED_QUERY_NOT_FOUND` proves an APQ cache, not a safelist; `PERSISTED_QUERY_NOT_SUPPORTED` proves APQ is off; neither proves what a second request with full text will do.
- **APQ request shape (exact)**: `extensions={"persistedQuery":{"version":1,"sha256Hash":"<sha256 of the document>"}}`, hash-only first; the miss response is the `PERSISTED_QUERY_NOT_FOUND` error; the follow-up carries both `query` and the same `extensions` object and is then cached. A hash that is not the exact SHA-256 of the supplied query is rejected, so a probe that "succeeds" with a mismatched hash is evidence of a different mechanism than APQ. `useGETForHashedQueries` makes the hash-only request a GET, which is what lets a CDN in front of the server cache the response — a cache-key question worth checking separately.
- **Status-code contract as a fingerprint** — deviations are evidence about enforcement, not decoration:

| Request | Draft expectation | What a deviation tells you |
|---|---|---|
| `GET` + mutation | `405` (MUST NOT execute) | a `200` with effects means the deployment is CSRF-capable |
| `POST` without `Content-Type` | 4xx (SHOULD reject) | `200` means the parser guesses a media type |
| unsupported request `Content-Type` | `415` | `200`/`400` means alternative encodings are accepted |
| malformed JSON body | `400` | parser/transport details in the body |
| document parse failure | `400` | engine-specific error vocabulary |
| validation failure | `422` | `400` vs `422` fingerprints the implementation |
| execution error with partial data | 2xx (`294` recommended) | `403`/`500` on partial data breaks read-back oracles |
| `Accept` with no supported type | `406` or ignore | content negotiation behavior of the gateway |
| batch when batching is disabled | — | Apollo Server answers `400`; GraphOS Router answers `BATCHING_NOT_ENABLED` |

- **Apollo Server HTTP behavior** (a common deployment): parse/validation failures and a blocked CSRF check return `400`; `GET` with a mutation, or any method other than `GET`/`POST`, returns `405`; a throwing `context` returns `500`; otherwise `200` even when execution produced errors. Apollo Server 4 returned `200` for variable-coercion errors (a regression) unless `status400ForVariableCoercionErrors: true` is set or v5 is used — so a "successful" 200 with coercion errors is a version signal, not a bypass. Apollo's CSRF prevention defaults to requiring a preflight-triggering request (JSON content type or a custom header) and blocks form-simple requests; its presence is why `application/x-www-form-urlencoded` probes fail on hardened deployments.
- **Batching defaults differ by server, and batching has real side effects.** Apollo Server 4 disables HTTP batching by default (`allowBatchedHttpRequests: true` re-enables it; Apollo Server 3 v3.5.0+ can disable it, earlier versions cannot). Apollo's GHSA-8r69-3cvp-wxc3 is the canonical batched-request impact: with batching enabled, per-operation `cache-control` headers were merged arbitrarily (fixed in AS 3.11.0 / 4.1.0), so a private operation batched with a cacheable one could be stored in a shared cache — a cache-poisoning vector, not just an authz concern. GraphOS Router batching is off by default (`batching.enabled: true`; `maximum_size` defaults to `null`, i.e. no limit); batched operations count individually for billing, batch errors are all-or-nothing (`BATCH_LIMIT_EXCEEDED`), and `@defer`/subscriptions are unsupported inside a batch.
- **Cost/alias limits are strategy-specific.** Apollo Router demand control scores operations with static weights (Query base 0, **Mutation base 10**, objects/interfaces/unions 1, **scalars and enums 0**) and rejects over-limit work only in `mode: enforce` (`measure` only records); list sizes come from a global `list_size`, per-subgraph overrides, or `@listSize`. Because scalar-returning fields carry zero weight, aliasing a scalar-returning operation (a login boolean, a token check) does not obviously raise the estimated cost — measure the deployed distribution (`cost.estimated`, `cost.delta`) instead of assuming an alias cap exists.
- **Router/server knobs to read before claiming a control exists** (all are off-by-default or opt-in, and a missing limit is not a bypass by itself): batching — `batching.enabled` (default `false`), `batching.mode: batch_http_link`, `batching.maximum_size` (default `null` = no limit), `batching.subgraph.all.enabled` / `batching.subgraph.subgraphs.<name>.enabled`, error `BATCHING_NOT_ENABLED` when a batch arrives disabled, metrics `apollo.router.operations.batching` / `.batching.size`; demand control — `demand_control.enabled` (default `false`), `mode: measure|enforce`, `strategy.static_estimated.list_size`, `strategy.static_estimated.max`, `strategy.static_estimated.subgraph.all.max`, `actual_cost_mode: by_subgraph|by_response_shape`; authorization — `authorization.directives.enabled` (default `true`), `reject_unauthorized` (default `false`), `errors.response: errors|extensions|disabled`, `errors.log`, `dry_run`; Apollo Server — `allowBatchedHttpRequests`, `persistedQueries`, `includeStacktraceInErrorResponses`, `status400ForVariableCoercionErrors`. Each knob changes the oracle's expected result, so capture the deployment's values (or infer them from the error/response shape) before testing.
- **Batching and aliasing are separate multipliers.** Aliases let one request return N instances of the same field (PortSwigger's aliased-login brute-force lab); list-based query batching packs N operations into one JSON array. Complexity/depth limits often cap neither — depth doesn't grow with aliases, and batch-count limits may be absent. The finding is one request performing N guards that N sequential requests would throttle.
- **Introspection is a type system you can traverse, not a single field.** The meta-types (`__Schema`, `__Type`, `__TypeKind`, `__Field`, `__InputValue`, `__EnumValue`, `__Directive`, `__DirectiveLocation`) are part of the schema, and `__typename` returns type names on any object/interface/union selection. Traversal continues through wrapper types (`ofType`) and fragment type conditions, so a partial blocklist still yields the graph one hop at a time — enumerate with a controlled query rather than a regex-shaped payload.
- Two fingerprints for directive enforcement: (1) `@authenticated` is documented as a **presence check** for the `apollo::authentication::jwt_claims` context key, so an authentication plugin that is disabled, misconfigured, or that skips signature verification makes every request "authenticated" while the schema still looks protected; (2) `@requiresScopes`/`@authenticated`/`@policy` on interfaces is a composition error from Federation v2.9 onward, so interface protection is expressed per implementing type and merged with AND — observed behavior at the interface boundary is the composition result, not the subgraph's intent.
- **Authorization directives are boolean expressions with composition rules.** `@requiresScopes(scopes: [["a","b"],["c"]])` is `(a AND b) OR c` (inner array = AND, nested arrays = OR); composition across subgraphs merges same/different directives with AND; interfaces combine implementations with AND, so an unauthenticated query against an interface whose *other* implementation is protected resolves `null` for the whole selection. Query deduplication groups authenticated queries by required-scope set, and `@include`/`@skip` never exempt a field from its directive. Each rule changes what a "denied" response looks like (empty data, `null` at a path, or a whole-query filter), so read the error path before concluding.
- **Introspection disabling is root-only.** GraphQL exposes introspection through the query-root meta-fields: `__typename` on any object/interface/union selection, and `__schema` on the query root (the spec also defines the `__type(name:)` lookup). Blocking `__schema` does not necessarily block `__type(name:)`, `__typename` traversal, or field-suggestion ("did you mean") leakage that tools like Clairvoyance/scrapers reconstruct; blocking on a naive regex is bypassed by case/whitespace/query-shape variants. Clairvoyance exists precisely because field-error suggestions recover the schema when introspection is off. Compare against a control query for a field you already know exists.
- **Federation helper fields bypass introspection controls.** Every subgraph built with `buildSubgraphSchema` gets `_service { sdl }` on its Query root, which returns the subgraph's SDL — disabling `__schema` has no effect on it, and it is enabled by default. `_entities(representations:)` lets a caller impersonate the router and resolve entity keys, and subgraph tracing data in `extensions` exposes internal service names and timing. The call shape is literal and stable — Apollo's own routing docs show the router emitting `query X($representations:[_Any!]!){_entities(representations:$representations){...on <Type>{...}}}` — so a probe can reuse a real plan's representation payload for a key the client was never allowed to fetch. `_entities` cannot be easily patched without router reconfiguration. If a subgraph is reachable directly (host/IP/port), both are exposed. Published mitigations, in order: keep subgraphs reachable only from the router (network policy/mTLS), enforce persisted queries, then filter `_service`/`_entities` in a plugin or middleware as a last resort — each is a precondition for whether the finding is reachable, so record which one is in place.
- **Schema reconstruction when introspection is off** is a wordlist problem, not a scanner problem: Clairvoyance drives field-suggestion errors to confirm type/field names, and its guidance is to seed the wordlist from HTTP traffic, mobile static files, or general English words; Apollo Server disables introspection automatically when `NODE_ENV=production`, so the tool's premise is a default deployment, not a misconfiguration.
- **Federation authorization directives are router-enforced and compose.** `@requiresScopes`, `@authenticated`, and `@policy` are turned on by default in GraphOS Router and are *not* supported by `@apollo/gateway`; unauthorized fields are filtered (`UNAUTHORIZED_FIELD_OR_TYPE`, `null` + error at the path). Two drift surfaces: (1) a directive on the root operation type composes onto the shared root merged type of *every* subgraph, so it silently applies to other teams' fields; (2) directives win over `@include`/`@skip` (a field excluded with `@include(if: false)` still produces an authorization error), and they do **not** affect introspection — protected fields remain visible when introspection is on. `@key` fields used for entity resolution are still fetched internally even when the client cannot query them.
- **Subscriptions sit outside the HTTP spec**: the GraphQL-over-HTTP draft states subscriptions are beyond its scope, so every subscription transport you meet is a community protocol (`graphql-transport-ws`, `graphql-sse`) or a framework extension, with no conformance suite behind the auth story.
- **Subscriptions have a two-phase auth model, and the transports differ.**
  - Over WebSocket (`graphql-transport-ws`): the socket negotiates, the client sends `connection_init` (auth payload rides here), the server replies `connection_ack`; executing before ack fails `4401 Unauthorized`, rejecting auth should close `4403 Forbidden`. Operations are `subscribe` messages with an `id`; multiple operations, including plain queries/mutations, multiplex on one socket. The protocol says the server *may* check permissions before executing an operation — it does not require it, and the protocol carries no per-operation credential.
  - Over SSE (`graphql-sse`): "distinct connections" mode issues one HTTP request per operation, so each operation inherits normal per-request auth; "single connection" mode establishes a reservation with a `PUT` (which may carry auth), returns a reservation token, then streams all results over one SSE connection whose only identity is that token — the spec explicitly allows the token in a URL search parameter for the native `EventSource`, and requires that exactly one SSE connection fulfils a reservation.
  - Bugs live where handshake auth is treated as operation auth, where a multiplexed connection holds one identity while subscribing to another tenant's topic, or where a long-lived subscription is never re-authorized after scopes change. Apollo's own `@policy` docs require re-evaluation at the execution service for subscriptions because a session's authorization can change after the stream starts.
  - WebSocket protocol fingerprint (all `graphql-transport-ws`): messages `connection_init`, `connection_ack`, `subscribe`/`next`/`error`/`complete`, `ping`/`pong`; close codes `4400` invalid message, `4401` unauthorized (operation before ack), `4403` forbidden (auth rejected), `4408` init timeout, `4409` duplicate subscriber id, `4429` too many init requests, `1000` normal closure. Queries and mutations are sent as `subscribe` messages on the same socket — a state-changing operation can ride an already-authenticated connection, and a connection whose mid-life token expires stays authorized until the socket closes.
  - SSE transport limits that shape deployments: HTTP/1.1 browsers cap concurrent connections per browser+domain (about 6), so servers adopt single-connection mode; HTTP/2 negotiates streams instead (commonly 100). In the SSE GraphQL protocol, validation failures must be delivered as `next` events rather than `4xx` (native `EventSource` cannot read a 400 body), `Content-Type` must be `text/event-stream`, and a `complete` event needs an empty `data:` field to fire on `EventSource`. One reservation must never back more than one SSE connection — a reservation token reused across sessions is the isolation bug to test.
- **Server implementations differ** on complexity/cost defaults, alias limits, persisted-query enforcement, and whether `GET` mutations are allowed; fingerprint the engine (Apollo Server, GraphOS Router, graphql-java, Hasura, Graphene, gqlgen, Spring GraphQL) from error shapes and extensions codes before assuming a limit exists.
- **Schema/source disclosure surfaces**: `_service { sdl }` (federation), error `locations`/`path`, and — in development — Apollo Server error `extensions.stacktrace` with resolver file paths; Apollo Server omits stacktrace when `NODE_ENV` is `production` or `test` unless `includeStacktraceInErrorResponses` forces it back on; message masking is likewise opt-in (`formatError`), so raw resolver messages (including database errors and embedded secrets) reach clients by default in every environment unless the deployment added a hook. Client-shipped `.map` files remain the other source of operation strings and schema fragments (see the artifact checklist below).

Transport matrix — what to fingerprint per endpoint before any CSRF or batching claim:

| Transport | Client can send | CSRF-exposed? | Notes |
|---|---|---|---|
| `POST application/json` | full operation + variables | normally no (opaque content-type) | the baseline; still needs a CSRF strategy if a token is accepted in a form |
| `POST application/x-www-form-urlencoded` | `query`/`variables` form fields | **yes** | PortSwigger CSRF lab; the fix is JSON-only |

### gRPC and gRPC-Web — metadata and proxy translation

- gRPC **metadata** is lowercase ASCII key/value pairs sent with a call; the wire ABNF for header names is `0-9 a-z _ - .` — uppercase is not in the grammar, so a case-varied HTTP header is normalized or dropped by different hops. Keys ending `-bin` carry binary values and are base64-encoded on the wire (padded and unpadded accepted; implementations emit unpadded). Names starting `grpc-` that are not defined by the spec are reserved and must not be used as custom metadata.
- The request **Content-Type** is `application/grpc` (optionally `+proto`/`+json`); a gRPC server should answer `415` when it does not begin with `application/grpc`. Requests carry `TE: trailers` to detect incompatible proxies. Responses may be **Trailers-Only**; `grpc-status` must be sent in trailers even when OK. Duplicate custom metadata values may be joined with `,`, and an implementation that parses one value where you sent two is a testable seam (grpc-gateway *appends* Authorization values rather than overwriting).
- Native frame layout (needed to hand-craft a probe): each message is a 1-byte `Compressed-Flag` (0/1), a 4-byte big-endian `Message-Length`, then the message; DATA frame boundaries do not align with message boundaries. Trailers are a final HEADERS frame carrying `grpc-status`; a response may be trailers-only. HTTP/2 header names are lower-case by framing, which is why the spec grammar has no uppercase.
- Native-wire details worth fingerprinting: `grpc-timeout` is `TimeoutValue` (at most 8 ASCII digits) plus a unit `H/M/S/m/u/n`; encoding rides `grpc-encoding` and `grpc-accept-encoding` (`identity`, `gzip`, `deflate`, `snappy`, custom); trailers carry `grpc-status` (decimal, no leading zeros), percent-encoded `grpc-message`, and `grpc-status-details-bin` (only when status is not OK, must not contradict it). Request header lists are suggested-capped at 8 KiB and response headers/trailers at 8 KiB each — a proxy that enforces a different cap than the backend is a request-shaping seam. Corrupt framing is signalled with `RST_STREAM`, which maps to INTERNAL/UNAVAILABLE/RESOURCE_EXHAUSTED/PERMISSION_DENIED and loses the application status — useful for distinguishing "proxy rejected" from "backend denied".
- **gRPC-Web** deliberately differs from native gRPC (per `PROTOCOL-WEB.md`) so a proxy can translate: `application/grpc-web` / `application/grpc-web+proto|+json`, plus `application/grpc-web-text` for base64 text streams (so XHR-only clients work). Header names may be upper/mixed case over HTTP/1.1, but **trailers encoded in the last length-prefixed message must be lower-case**; the trailer block is a plain HTTP/1 header block inside the body with the MSB of the first frame byte set. Client and bidi streaming are not part of the protocol — one more translation gap to fingerprint. `X-User-Agent` replaces `User-Agent`.
- gRPC-Web text mode and protocol bans: `Accept: application/grpc-web-text` asks for base64 text streams (default base64; `Content-Transfer-Encoding: base64` must not be used and padding may not align to message frames); stream-id, GOAWAY, and HTTP/2 PING are not used, the stream is closed by EOF, and bidi/client streaming is absent pending WHATWG streams. Any auth component that assumes a trailer status, a stream id, or client streaming will behave differently through this path. Content-type defaulting is another parser differential: `application/grpc-web` with no `+proto`/`+json` suffix is to be assumed `+proto` by the receiver, so a proxy or filter that instead guesses JSON parses the same call differently.
- **gRPC-Web browser features** define the CORS contract: `Access-Control-Allow-Credentials` for Authorization headers, `Access-Control-Allow-Methods` limited to `POST` and preflight `OPTIONS`, `Access-Control-Allow-Headers` matching whatever preflight carries, and `Access-Control-Expose-Headers` for `grpc-status,grpc-message`. A client may advertise request data/metadata as **URL query params** to avoid preflight, and the spec only says the proxy *should* remove them before the downstream call — a proxy that does not forwards client-controlled metadata. The client library is also expected to support header overwrites specifically to avoid preflight, which is another path where a browser-controlled header value reaches the backend. XSRF/XSS policy is listed as "to be published" in the spec, i.e. a genuine gap rather than a guarantee.
- **Envoy** provides the `grpc_web` filter (`envoy.extensions.filters.http.grpc_web.v3.GrpcWeb`, which follows `PROTOCOL-WEB.md`) and the header-to-metadata filter (`envoy.extensions.filters.http.header_to_metadata.v3.Config`), whose rules can read request/response **headers or cookies**, add dynamic metadata (e.g. into the `envoy.lb` namespace used for subset load balancing), apply regex rewrites, and can be scoped per route. If a route maps client HTTP headers (or cookies) into metadata the backend authorizes on, a client-controlled value becomes a trust claim. Record the proxy vendor/version and route config assumptions for every result. Its statistics counters (`request_metadata_added`, `header_value_too_long`, `base64_decode_failed`, `regex_substitution_failed`) reveal which conversion paths are configured, including whether values are base64-decoded — a config fingerprint you can often read from an exposed admin or metrics endpoint.
- **Envoy's gRPC-JSON transcoder** turns REST/JSON into gRPC given `google.api.http` annotations. By default it rewrites the request into `POST /<package>.<service>/<method>` and route configs match that path, not the incoming REST path, unless `match_incoming_request_route: true` is set. It forwards `x-envoy-original-path` and `x-envoy-original-method` to the gRPC server — headers the backend may trust. Route/method-based controls applied at the front door therefore see a different verb/path from the native gRPC call.
- **Transcoder JSON print options change the wire shape**: Envoy's transcoder exposes `print_options` including `preserve_proto_field_names` (default `false`, i.e. lowerCamelCase JSON), `always_print_primitive_fields`, and `always_print_enums_as_ints`. A backend authorization hook that keys on the proto spelling while the transcoder emits camelCase (or vice versa) is the same naming seam as the protobuf JSON mapping, one layer up.
- **grpc-gateway** (Go, `google.api.http` based) is a second transcoding surface: the incoming `Authorization` header **cannot be removed or overwritten** and is always forwarded as `authorization` metadata — but values can be appended; `WithIncomingHeaderMatcher` can promote arbitrary HTTP headers (e.g. `X-User-Id`) into metadata, and matching is case-insensitive over HTTP/1.1; `WithUnescapingMode` controls how much of the path is unescaped before routing (a routing-differential lever). For streaming methods the gateway emits newline-separated JSON chunks and, absent a custom `WithStreamErrorHandler`, includes the gRPC error code, message, and detail messages — an error-detail disclosure seam you can fingerprint without touching authz.
- **Reflection and health** (`grpc.reflection.v1alpha.ServerReflection`, `grpc.health.v1.Health`) give a service/method inventory without source; they are a fingerprinting aid, not a finding, unless they also expose payloads or bypass a metadata check.
- **Stream authorization** is a distinct seam from unary calls: initial metadata is checked once at stream open, and unary authz often runs only on the first message. The probe is acting as A on an authorized stream and referencing B's object mid-stream, then closing immediately.
- **gRPC-JSON transcoding** publishes a REST view of a gRPC method; authorization may be enforced on the gRPC side, the transcoded side, or neither. Run the same method through both and compare decisions. When the transcoder chooses the backing service/method from client input or from annotation mismatches, the same URL can reach two different RPCs.

Metadata handling matrix — the seam is proxy-vs-backend disagreement:

| Layer | Behaviour to fingerprint | Test |
|---|---|---|
| gRPC core | lowercase ASCII keys (`0-9 a-z _ - .`); `-bin` suffix = base64 binary value; `grpc-` reserved | send `Authorization` (capital) or `authorization-bin` and see which is honored |
| gRPC-Web (`PROTOCOL-WEB.md`) | trailers delivered as a length-prefixed message; lower-case trailer names required; no client/bidi streaming | a check relying on native trailers may not see the web-translated status |

### Protobuf and schema edge cases

- proto3 does not serialize fields set to their default (zero) value, so a server cannot distinguish "unset" from "explicitly zero" on the wire — an authorization or domain check that keys on a zero-valued field (an owner id of `0`, a `false` flag, an empty enum) can be satisfied by *omitting* the field. Probe by dropping the field entirely versus sending the zero.
- JSON mapping (protobuf HTTP/gRPC-JSON transcoding) accepts both the lowerCamelCase and the original `snake_case` field names and ignores unknown fields by default; a filter or authorization hook that inspects one spelling misses the other. Send both spellings with conflicting values.
- `oneof` and `Any` fields let a message carry a type the authorization layer did not anticipate; a hook that authorizes per known field can be bypassed by populating an unexpected branch of the union.
- Field numbers, not names, are the wire contract: a renamed/removed field reuses a number, so a legacy client and the current server can disagree about semantics while both "validate" — relevant when mining version drift from descriptors.

### SSE and WebTransport — transport-shaped auth

- `EventSource` cannot set custom request headers in any mainstream browser generation, so an SSE endpoint authentically protected by an `Authorization` header is structurally unreachable from the browser; deployments compensate with a cookie session (equal authz) or leave a weaker path (token in query string, no auth). Enumerate both the browser path and the direct-HTTP path.
- SSE reconnection semantics are specified: `withCredentials: true` sets the request credentials mode to `include` (default is anonymous — cross-origin cookies are not sent); the server's last `id:` value becomes a **`Last-Event-ID`** request header on reconnect (any UTF-8 string without NULL/LF/CR); `retry:` sets the reconnection delay; `204 No Content` stops reconnection, while `301`/`307` redirects are followed and non-200 or wrong `Content-Type` fails the connection. The event's `origin` is the final URL after redirects. If the server trusts `Last-Event-ID` without scoping it to the subscriber, reconnect replays another principal's events; a permissive CORS reflection plus credentialed SSE is an isolation risk.
- SSE wire format details that matter when you forge or replay events: a blank line dispatches the buffered event; fields are `data`, `event`, `id`, and `retry` (compared literally, no case folding); an `id` field with an empty value clears the last event ID so no `Last-Event-ID` is sent next reconnect; comment lines (`: keepalive`) are the documented workaround for proxy idle timeouts and chunking can distort event timing. Forging a stream is a server-side test only — the client-side oracle is what the server accepts on reconnect and which subscriber's events it returns.
- GraphQL-over-SSE "single connection" mode makes the seam explicit: a `PUT` reservation (which may carry auth) returns a reservation token; the token rides either the `X-GraphQL-Event-Stream-Token` header or a `?token=` search parameter, and one reservation must map to exactly one SSE connection. Operations are separate HTTP requests whose results stream over that connection, so any authorization that is not re-checked per operation is inherited from the reservation.
- **WebTransport** runs over HTTP/3 and exposes reliable streams, unreliable datagrams (RFC 9297 HTTP Datagrams / QUIC DATAGRAM), and session establishment via an HTTP/3 `CONNECT`. The W3C spec fixes several properties a tester must not misread: the session request uses credentials mode **`omit`**, cache mode `no-store`, and redirect mode `error` — redirects are not followed and redirect-induced network errors are deliberately indistinguishable from other errors. Authentication therefore arrives through the `headers` option on the constructor (or a separate authenticated bootstrap), not through cookies, and is then assumed for the whole session. Per-stream/per-datagram authorization is often missing where the session was authenticated once; server-initiated streams (`incomingUnidirectionalStreams`, `incomingBidirectionalStreams`) appear on that session's authority. `serverCertificateHashes` allows a pinned SHA-256 certificate hash for dedicated connections. QUIC adds 0-RTT and connection migration — cross-read the http-edge-cache pack when the transport itself is suspect, keep channel-authz findings here. Session lifecycle is visible to the client: `ready` resolves on establishment, `closed` carries a `WebTransportError`, `draining` fires when the server wants the client to stop opening streams, and `protocol` exposes the negotiated sub-protocol — a drain is a forced re-authentication point, so check whether streams opened after a re-established session inherit the new identity or the old authority.
- **Correction to earlier pack text**: the previous note that auth is "frequently established by that fetch (cookies/headers)" is right about custom headers but wrong about cookies — the WebTransport handshake is credentials-mode `omit`, so a cookie session does not ride the `CONNECT`; cookie-based deployments must bootstrap the token out of band.

| Transport | Header control | Cookie control | Channel model | Auth seam |
|---|---|---|---|---|
| SSE (`EventSource`) | none (no custom headers) | `withCredentials` for cross-origin | one event stream per connection | token in query, `Last-Event-ID` replay, single-connection reservation token |
| WebSocket | `Sec-WebSocket-*` negotiated at handshake | yes (Origin-scoped) | multiplexed frames | handshake auth treated as per-message auth; ops never re-authorized |
| WebTransport | `headers` option on the session request | **no** (credentials mode `omit`) | streams + datagrams, per-session | session auth assumed for every stream/datagram; header-delivered token |

### BFF / gateway translation differentials

- A **BFF / token-handler** keeps OAuth tokens server-side and gives the browser only a session cookie; the BFF then calls upstreams with real tokens and (often) injected identity headers. Two seams follow: (1) the browser-facing session authz vs the upstream token authz can disagree; (2) any header the BFF injects (`X-User-Id`, `X-Scopes`, `X-Tenant`) is a trust claim — if the upstream accepts a client-supplied copy, or the BFF passes a client header through, the principal is forgeable.
- The OAuth browser-apps draft defines the BFF contract precisely: the BFF is a **confidential OAuth client**, manages access/refresh tokens inside a cookie-based session so no token reaches the browser, and **MUST implement CSRF defence** for browser→BFF calls (CORS is an accepted mechanism). It also **MUST validate destination hosts before forwarding** and keep an explicit allowlist of approved resource servers — because a BFF tricked into forwarding to an arbitrary host leaks the user's access token. That is the highest-value BFF differential to test: client-controlled destination (host, base URL, tenant, path prefix) + a server-held token.
- The draft's third pattern, the **token-mediating backend**, is the differential to look for when the frontend does hold a token: the backend handles the OAuth exchange but hands the access token to the browser app, which then calls resource servers directly. That inverts the BFF threat model — token theft from the browser (XSS, storage, service worker) is in scope again, and the resource servers, not the backend, enforce scope. Identify which pattern is deployed before choosing the seam. Session storage is the third variable: server-side cookie sessions expose only a session ID and support revocation, while client-side (signed/encrypted) cookie sessions push state into the browser and make revocation hard — a BFF that cannot revoke is the one where a stolen cookie outlives the logout you will use as a control.
- Gateway path/method normalization is vendor-specific: `/api/../admin`, duplicate slashes, encoded slashes, case-folding, and `X-Original-URL`/`X-Rewrite-URL` are read by different hops at different stages. The bug is a hop that authorizes on the *normalized* path while the origin routes on the *raw* path (or vice versa). Re-fingerprint after any gateway version/vendor change observed mid-engagement.
- Content-type/parameter precedence: a gateway that validates JSON but forwards to a handler that also binds form/query parameters lets a request carry both, with the handler choosing the unvalidated one. The same applies one layer down when a transcoder reconstructs the RPC from whichever representation it prefers.

BFF / gateway seam table:

| Seam | What to send | Expected-safe | Vulnerable |
|---|---|---|---|
| Injected identity header | `X-User-Id: <victim>` direct to upstream | upstream overwrites from verified session | client value reaches the authz decision |
| Trusted routing header | `X-Original-URL: /admin` | gateway ignores/overwrites | origin routes by the client value |
| Path form | `/admin`, `/api/../admin`, `/%2e%2e/admin` | one canonical decision | gateway and origin normalize differently |
| Method override | `POST` + `X-HTTP-Method-Override: DELETE` | consistent method | outer method authorized, inner executed |
| Token boundary | reach the upstream with the BFF session cookie only | upstream requires its own token | upstream trusts the BFF session/header |
| Outbound destination | BFF endpoint + client-controlled upstream host/path | allowlist rejects non-approved hosts | BFF forwards the user's token to the supplied host |

### Webhooks and callbacks

- A registration endpoint that accepts a researcher-controlled delivery URL is a server-side fetch primitive: observe delivery (headers, source IP, whether an HMAC secret is included) on a collaborator **before** considering any internal target. The safe, reportable unit is the primitive, not an SSRF that touches internal ranges.
- Properties to fingerprint: allowlist or domain-ownership verification, redirect following, private-range/metadata blocking, retry cadence, and whether the signing secret is a header versus a URL parameter. Delivery that reaches an unverified domain with a reusable secret is the finding.

### Version drift mined from shipped bundles

- Enumerate versions from evidence rather than guessing: `//# sourceMappingURL` (and shipped `.map` files) reconstruct original routes and parameter names; webpack/vite chunk names and dynamic `import()` paths reveal lazy routes the crawl never reaches; GraphQL operation names embedded in client code map to the schema without introspection; mobile apps ship protobuf/OpenAPI descriptors.
- The finding is a **decision differential** between versions, not the existence of a legacy route: `/v1/` vs `/v2/`, `/internal/` vs `/public/`, or a deprecated field still honored. Compare the same operation's authorization outcome across versions with two accounts, and treat identical decisions with different shapes as version drift in format only. RFC 8594 `Sunset` headers tell you which versions the operator believes it has retired — a live response from one of those is drift. The header announces the decommission stage only (when the URI becomes unresponsive), not mere "not preferred" deprecation, so its presence is not itself a finding and its expiry is only a finding if the behavior (not just the response) survives.

Artifact-mining checklist (evidence first, no spraying):

1. JS bundles: `//# sourceMappingURL`, shipped `.map`, webpack/vite chunk names, dynamic `import()` targets, hard-coded API hostnames and version strings.
2. Client operation names: GraphQL operation/field names in queries, REST route strings, gRPC method paths — these seed the representation table without introspection.
3. Mobile binaries: protobuf descriptors, OpenAPI/Swagger JSON, embedded base URLs, feature flags that gate a route.
4. Server-origin signals: `Server`/`Via`/`X-Powered-By` headers, CORS `Access-Control-Allow-*` reflecting an admin path, error-message vocabulary that names internal routes.
5. Documentation drift: an OpenAPI file the running service does not honor, or a deprecated endpoint the docs still describe.
6. Map each discovered capability to the version/representation table used for the differentials (see the matrix below).

Cross-representation differential matrix (hunt the cell that disagrees):

| Capability | Representation A | Representation B | Typical disagreement |
|---|---|---|---|
| Read one object | REST `GET /v2/obj/:id` | GraphQL `obj(id:)` | GraphQL resolves without the owning-tenant check |
| Read one object | router `obj(id:)` | subgraph `_entities(representations:)` | entity lookup skips the field-level directive |
| Update one object | REST `PATCH` | gRPC-JSON transcoded `PATCH` | transcoded path skips the gRPC authz interceptor |
| List/filter | REST list | aggregate/count endpoint | count discloses cross-principal totals |
| Paginate | list page 1 | continuation/cursor token | cursor is not re-bound to the principal |
| Auth/session | web cookie session | mobile bearer / API key | mobile token skips MFA/step-up |
| Scoped key | key restricted to API A | API B / internal service | restriction checked per-API, not enforced on B |
| Admin function | gateway frontdoor | direct origin / `X-Original-URL` | origin serves the function the gateway gates |
| Stream events | SSE cookie session | WebSocket handshake auth | per-event authz missing on the stream |
